# カラーシステム (設計案)

この文書は**まだ確定していない設計案**である。ここで「決めること」に挙げた分岐に裁定が付いたら本文を確定版に直し、それから CSS に適用する。適用後は、新しい部品は本文の語彙表にある名前だけを使う。

## 1. 目的

**色を決める作業を、数個の入力を選ぶことに閉じる。** 入力以外の色はすべて算出結果であり、人が値を選ぶ場所ではない。画面を見ながら入力を差し替えて見比べられる。

増やしたくないもの (これが増えるなら、その設計は採らない):

- **生の色値**。部品の CSS に書かれた hex / oklch のリテラル。
- **部品ごとの色の発明**。「この画面のこの帯だけの色」を、既存の語彙に無いまま足すこと。
- **light と dark の二重定義**。同じ役割の色を、light 用と dark 用に人が別々に選ぶこと。
- **一つの名前が複数の意味を兼ねること**。意味が増えたら名前を増やすか、その意味は色以外で表す。

「入力」だけは人が選ぶ。それ以外に人が色を選べる場所を作らない。

### 2.4 棚卸しから見えること

- **面は地より明るい。** light で `--surface` (L 1.000) が `--bg` (L .985) より明るく、dark でも `--surface` (.238) が `--bg` (.203) より明るい。つまり面は両方のテーマで「白い側」へ置かれている。地から文字へ向かって単調に並ぶ段の列に、面はそのままでは乗らない (§5.3)。
- **中立の色味が light と dark で別方向。** light の中立は h ≈ 80〜85 の暖色、dark は h ≈ 295〜297 の紫寄り。中立の色味を入力 1 個で持つと、どちらかが今と変わる。
- **`--live` が 4 つの意味を兼ねている。** 接続が生きている / 返信である / 使った量 / 費用の系列 1。色が同じでも意味は別で、片方を変えたい時に動かせない。
- **識別のための色が 2 系統ある。** 検索は生 hex 6 色、費用の内訳は意味色を 6 つ借りている。どちらも「見分けが付けばよい」色で、意味は無い。
- **半透明が語彙の外にある。** 混色 6 箇所と `opacity` 7 箇所は、どの意味の色なのかが名前で表れていない。
- **罫のコントラストが 1.3。** WCAG 2 の 1.4.11 が求める 3:1 に対して、面の上の罫は light 1.32 / dark 1.31。入力欄の枠のように「そこに部品があること」を罫だけで示している箇所は現状で基準を満たしていない。
- **`--waiting` の文字が light で 4.1。** 4.5 に届いていない。
- **dark の見た目に基準が無い。** `test/visual` の 27 枚は `colorScheme: "light"` で撮っている。色を触る変更の差分は、いまのところ light しか見えない。

## 3. 3 層

```
層 0  入力        人が選ぶ数個の値 (色相・色味・light|dark)
        │  段表 (§5) で機械的に展開
層 1  段          --<色相>-1 … --<色相>-n   色相ごとの階段
        │  段番号と役割の対応は全色相で共通
層 2  意味名      --bg / --surface / --border / --fg-muted / --accent / --waiting …
        │
部品の CSS        層 2 の名前だけを参照する
```

規則は 3 つ。

- **部品の CSS は層 2 だけを参照する。** 層 1 を直接書かない。層 0 は部品から見えない。
- **層 2 の語彙は閉じている** (§6 の表がすべて)。新しい意味名は、この表に足してから使う。表に足せない色が要ると思ったら、それは色ではなく別の手段で表す対象かもしれないと疑う。
- **段番号は役割を指す。** `--gray-5` と `--danger-5` は同じ役割なので、「この場面だけ中立を危険に差し替える」が段番号を変えずに書ける。

## 4. 層 0: 入力

| 入力 | 型 | いまの値に相当するもの |
|---|---|---|
| `--brand` | oklch 色 | light `oklch(.478 .082 253)` / dark `oklch(.761 .075 252)` |
| `--neutral-h` | 色相 | light 85 / dark 296 |
| `--neutral-c` | 0〜.03 | light .006 / dark .010 |
| `--h-live` | 色相 | 152 |
| `--h-waiting` | 色相 | 76 |
| `--h-danger` | 色相 | 32 |
| `--tag-h0` / `--tag-step` | 色相・度 | 識別のための色の並び (§9) |
| light / dark | 切替 | OS 設定、または `:root[data-theme]` |

`--brand` は light と dark で別の値を取る。段の L はテーマごとの段表が決めるので、入力として与えるのは実質 h と C だが、カラーピッカーで選べるのは「色」なので色として持ち、段表側で L を上書きする。

状態の色相を brand から回して作らない。brand が赤や緑になった瞬間に意味が衝突する。

light と dark の切替は `@media (prefers-color-scheme: dark)` を残したまま `:root[data-theme="light|dark"]` を優先させる。画面を見ながら両方を見比べるのに要る。

### 5.1 段と役割

| 段 | 役割 | 中立での例 |
|---|---|---|
| 1 | 地 | ページの地、入れ子の面の地 |
| 2 | 面 | カード、一覧、吹き出し、入力欄 |
| 3 | 面 (hover) | 行の hover、メニュー項目、表の見出しセル |
| 4 | 面 (選択・指し示し) | 選択行、プレビューの指定行 |
| 5 | 罫 | 枠、区切り線 |
| 6 | 罫 (hover・フォーカス) | 押せることを示す枠 |

色相付きの段も同じ番号で同じ役割を持つ。`--waiting-4` は「待ちの色を薄く敷いた面」、`--waiting-7` は「待ちの色の塗り」、`--waiting-8` は「待ちの色の文字と罫」。いまの `--waiting` 1 個が担っている 3 つの用法が、3 つの段に分かれる。

### 5.2 L と C の設計値 (暫定)

L は現状の実測値を足場にした暫定値で、適用時に測り直す。

| 段 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
|---|---|---|---|---|---|---|---|---|---|
| light L | .985 | 1.00 | .955 | .93 | .90 | .84 | .55 | .52 | .25 |
| dark L | .203 | .238 | .28 | .32 | .36 | .44 | .72 | .66 | .92 |
| C 係数 | .1 | .05 | .3 | .5 | .5 | .8 | 1.0 | .9 | .1 |

C 係数は入力の C に掛ける。中立は `--neutral-c` を段によらず一定で掛ける。

- 1〜4 は面同士なので差を小さく取る。4→5 で罫に飛び、6→7 で塗りに飛ぶ。
- 7 (塗り) と 8 (文字) は L が近い。塗りの上に乗る文字は段 1 か 2 を使う (`.held-badge` の現状と同じ)。
- 9 と 1〜2 の差が本文のコントラスト、8 と 1〜2 の差が弱い文字のコントラストを決める。合否は L 差ではなく最終色で測る (§8)。

### 5.3 面が地より明るいこと

段 2 (面) の L は、light では段 1 より**高く**、dark でも段 1 より**高い**。段の列は「地から文字へ単調に遠ざかる」形にはならない。

これは表にそう書けば済むことで、構造の破綻ではない。段番号が指すのは役割であって L の順序ではない。色相付きの段 2 は「色の付いた面」として light では地より少し暗くなるが、それは面に色を混ぜれば暗くなるという当たり前の結果で、中立の面が最も明るいのは無彩色だからである。

温かい地の上に白い紙が乗っている、という現状の見え方を残すかどうかは §12 の A。

## 7. 色空間と算出

**oklch に一本化する。** 段を作る操作は「同じ色相のまま L と C を動かす」ことで、oklch はそれを直接書ける。hsl は同じ L でも色相によって明るさが変わるので段表が成立しない。

**算出は CSS の相対色構文で行う。JS で色を計算しない。**

```css
--danger-8: oklch(from var(--danger-seed) var(--l-8) calc(c * var(--c-8)) h);
```

入力を `:root` に書き換えれば全段が再計算される。テーマを切り替える処理が「入力変数を書く」だけになり、色の算出規則が CSS の中にあるまま (= app.css を読めばテーマの仕組みが分かる) になる。ビルド時に色表を生成する形は、画面を見ながら入力を差し替える用途と両立しない。

段の L / C を `@property` で型付けしておくと、テーマを切り替えた時に段が補間される。切替を一瞬で行うなら不要なので、適用してから決める。

### ブラウザ対応 (公開情報。この環境での実測はしていない)

| 機能 | Chrome | Safari | Firefox |
|---|---|---|---|
| `oklch()` | 111 | 15.4 | 113 |
| `color-mix()` | 111 | 16.2 | 113 |
| 相対色構文 `oklch(from …)` | 119 | 16.4 | 128 |
| `@property` | 85 | 16.4 | 128 |
| `light-dark()` | 123 | 17.5 | 120 |

相対色構文に乗ると下限は Safari 16.4 相当になる。`light-dark()` は下限をさらに上げるうえ、`@media` と `[data-theme]` の二段構えで同じことができるので使わない。

### ガマット

oklch は sRGB より広い色を書けるので、段の C を上げると画面外の色になる。CSS の変換は L と h を保って C を下げるので、外に出た段は同じ色相のまま濁る。黄〜橙 (h 60〜100) の暗い段で先に起きる。§5.2 の C 係数はこの範囲に収まることを狙った値で、濁りが実測で出た色相はその色相の上限係数を下げる。

## 8. コントラストの保証

**保証は段表に閉じ込める。** 入力から触れるのは色相と色味で、L は触れない。段表が light / dark それぞれで基準を満たすように作られていれば、どんな入力でも文字は読める。色相によって最終的な輝度は動くので、段表だけでは保証しきれない分は検査で見る。

検査は CSS の式では書けない (WCAG 2 の比は最終的な sRGB の輝度で決まる)。`getComputedStyle` で解決済みの色を読み、次の組で比を出す小さな画面を持つ:

| 組 | 基準 |
|---|---|
| 段 9 / 段 1・2 | 4.5 |
| 段 8 / 段 1・2 (中立と全状態色) | 4.5 |
| 段 1・2 / 段 7 (塗りの上の文字) | 4.5 |
| 段 5・6 / 段 1・2 (罫) | 3.0 |
| `--tag-*` の上の文字 | 4.5 |

基準を割った組は警告として出す。直すのは人で、画面が入力を書き換えることはしない。

いまの値では `--waiting` の文字 (light 4.1) と罫 (light 1.32 / dark 1.31) がこの検査に落ちる。段表を基準に合わせると、罫は今より濃くなり、待ちの文字は今より暗くなる。**見た目が変わる**ので、適用は §11 の段 2 で行う (段 1 は見た目を変えない)。

## 9. 識別のための色

検索語ごとの帯と、費用の内訳の系列は「見分けが付けばよい」色で、意味を持たない。意味色から借りると、緑の系列が「正常」に見えてしまう。

これらは**段に色相を並べたもの**として持つ: `--tag-N = oklch(var(--l-3) calc(var(--c-3) * …) calc(var(--tag-h0) + N * var(--tag-step)))`。

段から作る利点が 2 つある。dark では段 3 が暗くなるので、明るい帯に暗い文字を載せている現状の dark 対応 (`color: #17161a` の直書き) が要らなくなる。そして色の数を増やしても値を選ぶ必要が無い。

話者ごとの色は今の画面に無い (`incoming` / `reply` / `notice` が `accent` / `live` / `waiting` を借りている)。持つなら同じ仕組みで色相を割り当てることになるが、持つかどうかは §12 の E。

## 10. Shiki

コードのハイライトは `github-light` / `github-dark` が持つ色をトークンごとにインラインで受けている。これは**この体系に接続しない**。構文の色は「面の上の役割」ではなく言語の構造を表すもので、段に対応が付かない。入力を変えてもコードの色は変わらない。

接続するのは、コードブロックの**地と罫**だけ (段 2 と段 5)。

## 11. 適用の段階

1. **語彙を置き、生の値を層 2 経由にする。** 意味名を `:root` に定義し、現状の値をそのまま入れる。検索の 6 色・影・混色 6 箇所を名前に置き換える。**見た目は変えない** — `test/visual` の 27 枚に差分が出たらそれは間違い。
2. **層 1 と層 0 を入れる。** 段表から意味名を算出し、入力を 1 箇所にまとめる。§8 の検査画面をここで作る。**ここで見た目が変わる** (罫が濃くなる、待ちの文字が暗くなる、dark の検索の帯が暗くなる)。差分を 1 枚ずつ見て基準を撮り直す。
3. **テーマエディタ。** 画面に重なるフローティングの面で、入力をカラーピッカーとスライダで触る。テーマを丸ごと差し替えて見比べる。保存先と差し替えの仕組みは、この段に入る前に別途決める。

段 2 の前に、`test/visual` に dark を足す (`colorScheme: "dark"` の 27 枚)。足さないと、色を触る変更の半分が見えないまま進むことになる。

## 12. 決めること

### A. 面と地のどちらを明るくするか

いまは温かい地 (`#fbfaf8`) の上に白い紙 (`#ffffff`) が乗っている。段の列に面が乗らない (§5.3) 原因はここにある。

1. **いまのまま** (段 2 の L を段 1 より高く取る)。紙が浮いて見える表現を残す。段表が 1 箇所だけ非単調になる。
2. **地を白、面を薄い灰にする** (段 1 が最も明るい)。段表が単調になる。白い紙の表現は無くなり、light の見た目が変わる。
3. **地と面を同じ色にし、罫だけで分ける**。段が 1 つ減る。情報密度の高い一覧では境界が読みにくくなる。

**推し: 1。** 非単調なのは表の値であって構造ではなく、§5.3 のとおり色相付きの段では自然に解決する。見た目を変えない案でもある。

### B. 段の数

1. **9 段** (§5.1)。いま画面が実際に使っている役割の数と一致する。
2. **12 段** (Radix Colors と同じ刻み)。面を 5 段、罫を 3 段、塗りを 2 段に分ける。外の資料と段番号で会話できる。使われない段ができる。

**推し: 1。** 使われない段は「どれを使えばいいか分からない」を生む。足りなくなったら足せる。

### C. 状態の色の名前

いまは `--live` / `--waiting` / `--danger`。

1. **いまの名前を残す。** `live` は「生きている」であって「成功」ではなく、この画面が表しているのは実際に接続や進行の生死。ただし `--live` が兼ねている 4 つの意味 (接続 / 返信 / 使用量 / 系列) のうち、返信と系列は §9 と別の手段へ移す。
2. **`success` / `warn` / `error` に寄せる。** 外の語彙と揃う。この画面には「成功した」と言いたい場面がほとんど無い。
3. **1 に `--info` を足す。** brand と別の「知らせ」の色を持つ。いまは brand が兼ねている。

**推し: 1。** 名前は画面が言っていることに合っている。`--info` は使う場面が現れてから足す。

### D. 識別のための色を独立させるか

1. **独立した色相の並びにする** (§9)。検索と費用の両方がこれを使う。意味色と混ざらない。入力が 2 個増える。
2. **意味色を借り続ける。** 入力が増えない。緑の系列が「正常」に見える。検索の帯は生 hex のままか、意味色の薄い段から作る。

**推し: 1。** 色の数が増えても値を選ばずに済むのが効く。

### E. 話者ごとの色を持つか

1. **持たない。** いまの `incoming` / `reply` / `notice` の左罫 (accent / live / waiting) を続ける。誰の発言かは名前で読む。
2. **固定のスロットだけ持つ。** 自分と相手の 2 色を入力に置き、それ以外は中立。
3. **色相を割り当てる。** 参加者ごとに空いている色相を配り、吹き出しの地・罫・アバターを同じ色相の別の段から取る。

**推し: 1。** 画面にいま無いものを、色の体系を決めるのと同時に入れない。3 は割り当ての仕組み (誰にいつ何色を配り、いつまで固定するか) がそれ自体で 1 つの設計になるので、要ると分かってから別に決める。

### F. 半透明で作っている色

混色 6 箇所と影 1 箇所。

1. **段から作り直す** (`--surface-hover` = gray-3 のように不透明な色として持つ)。上に何が来ても同じ見え方になる。重なった面の上では地が透けない。
2. **半透明のまま名前を付ける** (`--surface-hover: oklch(from var(--gray-9) l c h / 6%)`)。入れ子の面の上でも「その面より少し濃い」が成り立つ。最終色が文脈で変わるので §8 の検査が効かない。

**推し: 1。** 検査できることを優先する。入れ子の面 (`.tl-aside` など) は自分の地を持っているので、不透明でも破綻しない。
