# ccmsg-webui 設計

> 🇬🇧 [DESIGN.md](./DESIGN.md)

## ドメイン

このリポジトリが持つのは **契約の読み手 1 つ**。daemon が push するものを畳んで見せ、人の操作を op に変えて送る。ドメインの語彙 (セッションとは何か、分類はどう決まるか、topic はどう畳むか) は全て契約側にあり、ここには置かない。

このページは **自分の origin で publish される** 静的サイトで、繋ぐ先は自分の URL で publish された instance (契約 `Endpoint`)。daemon が 1 つの proxy の後ろで UI ごと配っている置き方では同じホストになり、それ以外では別の site になる。**1 つではなく 2 つの住所であること**が設計の起点で、次の 3 つがそこから出る。

- **繋ぐ先は述べるもので、推測しない**。接続バーで打ち、次の訪問まで覚える。このページ自身の住所は、入力欄に最初から入っている値にすぎない (`src/auth/endpoint.ts`)。2 つを突き合わせることは無い — passkey が答えるのは「どの origin で作られたか」だけで、どの instance に入ってよいかは所有 record が答える (契約 DR-0030)
- **入口の許可は passkey**。誰が来たかに答えるのは access token で、origin の許可集合は無い (下記「人の認証」)
- **世代が違えば話さない**。互換経路は持たず、リロードを促す (契約「版と互換」)

## 層

| 層 | ファイル | 責務 |
|---|---|---|
| 接続 | `src/connection.ts` | socket の生死、`hello.user`、request と reply の相関、再接続、購読の復元 |
| 畳み | `src/topic-fold.ts` | topic frame を手元の値に畳む。規則は契約の `granularity` |
| 状態 | `src/state.ts` | signal と、その唯一の書き手である関数 |
| 派生 | `src/sessions.ts` `src/runs.ts` `src/route.ts` | 並び・セクション・表示名・run を名指す住所の読み方・URL 文法 (純関数) |
| base | `src/base.ts` | この成果物が配られた場所と、それを起点にした route の読み書き |
| transcript | `src/timeline/` | 型付き item を画面の並びに読む純関数層と、購読・取り寄せを束ねる `TranscriptItemsView` |
| 画面 | `src/ui/` | 読むだけ |

状態層は `@preact/signals`。更新関数を state module に集約したものが action で、`useMemo` / `memo` は置かない (DR-0032 §2.1)。

## topic の畳み方は契約から引く

`TopicFold` は topic 名から契約の `topicGranularity()` を引いて畳む。webui 側にどの topic がどう畳むかの表は無く、契約に topic が増えてもこのファイルは変わらない。

畳んだ結果は常に **(instance, payload) のスロットの列**で、`whole` と `per_instance_whole` はスロットの鍵が違うだけの同じ操作になる (前者は topic に 1 つ、後者は instance に 1 つ)。読む側は 1 つの形だけを読む。instance ごとの全体を横断で足すのが `union()` で、これが契約の言う「手元の値は instance 横断の和」にあたる。

`append` は列に畳めない。手元に残るのは instance が全体として言った値ではなく、伸び続ける値の**一続きの区間**なので、`AppendFold` が別に持つ: 窓 (`start`/`end`/`lines`) と、instance が最後に言った全長 (`size`)。窓は 2 方向から埋まる — frame が末尾に足し、`transcript.read` が先頭に足す。どちらでもないもの (隣接も重複もしない区間) は**穴**で、穴は繋がっているふりをせず拒否する。offset は byte で、契約の read が刻む offset と同じものなので、生で届いたものと読んで戻したものが二重に数えられることなく繋がる。

**`element` は畳まない**。購読する画面がまだ無く、畳めない topic を購読して「空」として読ませないために、購読時点で拒否する (`isFoldable`)。

instance との接続が切れたら、その instance が言ったことは捨てる。止まった値は生きた値と見分けが付かない。

## Timeline の 3 層

transcript は「取得」「モデル」「描画」の 3 層に分ける。

| 層 | ファイル | 責務 |
|---|---|---|
| 取得 | `src/timeline/items-view.ts` | `transcript.items:<sid>` の購読、`transcript.items.read` の遡り読み、`transcript.read` による生 record の取り寄せ |
| モデル | `src/timeline/items.ts` `src/timeline/item-view.ts` `src/timeline/display.ts` | 型付き item → 呼び出しと答えの結合・畳みのまとめ → `TimelineNode`、型ごとの名乗りと中身、そして型ごとの表示属性。純関数のみ |
| 描画 | `src/ui/Timeline.tsx`, `src/markdown/` | nodes を読むだけ。スクロール位置の意味付け、Markdown の読み方、fold の見た目もここ |

**分類は instance、契約は型の語彙、webui は jsonl を読まない**。transcript は harness が自分の都合で書いている file なので、どの record がどの item かを決めるのは file を持っている側になる。webui に届くのは分類された item だけで、ここには record の形が 1 つも書かれていない — harness が file を変えても、別の harness が読まれるようになっても、この層は動かない。

**呼び出しと答えは 2 つの言い方で結ぶ**。答えは、読んだ側が付けた item の id (`parent_item`) と、harness が呼び出しと答えを組にした鍵 (`parent_tool_use_id`) の両方で親を指す。前者は instance がその呼び出しを読めていた時だけ付くので、**無いのは正常** — 頁の途中から読み始めれば、答えより前に居る呼び出しは instance の読んだ範囲の外に居る。webui は前者が手元で引けるならそれを使い、引けなければ鍵で手元の呼び出しに突き合わせる: 呼び出しは前の頁で既に持っていることがあり、その時は結び直せる。呼び出しを読めなかった答えは `tool.unknown` (どの道具だったかは record に書かれていない) として届くので、名乗りと中身は汎用形のまま、結び直せた時だけ呼び出しの下に入る。

**生の record は取り寄せで見る**。item が答えられない唯一の問いが「元の行は何と書いてあったか」で、item はその住所 (`source`) を持っている。各 item の下の `jsonl` を開くと `transcript.read` をその 1 record に絞って頼み、返った行を整形して出す。既定で目立つのは**汎用形で出ている item** (`system.unknown`、専用の見た目を持たない道具・添付・知らない型) — そこが分類の甘い所で、元の行を見ないと分からない所だから。1 つの record から読まれた item は同じ住所を指すので、取り寄せは record ごとに 1 度で足りる。

**購読が先、読み込みが後**。逆にすると、読み終わってから購読するまでに分類された分がどちらにも入らない。購読の snapshot は末尾 200 item を運び、同じ item が読み込みと重なっても id で数えるので二重にならない。

**画面が持つのは末尾 1 MiB 相当**。追い続ける値は伸び続けるので、上限が無ければ開きっぱなしのタブは全部を抱える。数えるのは item そのものの重さで、下限は snapshot が運ぶ 200 item (受け取った端から手放す窓は、同じものを永久に頼み続ける)。手放すのは末尾が伸びた時だけで、読み手が求めて遡った頁を、それを取ってきた read が取り上げることはない。手放した item に付いていた fold の開閉 (`fold:<item id>` / `msg:<item id>` / `think:<item id>` / `raw:<record id>`) も同じ契機で消す: 無いものの開閉は残しても意味を持たず、遡って戻ってきた item は読み手の既定から始まる。

**読むのは下限を置かずに**頼む。下限の無い読みは範囲の**新しい側**を答えるので (`prev` がその 1 つ手前を名指す)、末尾から 1 頁ずつ手前へ歩ける。上限は**手元の先頭 item** (`until_id`、その item は含まない) で、返った `prev` と同じものを指す — 覚えた `prev` を使うと、窓が先頭を手放した後にそれが「もう無い item」を名指して、間に穴が開く。何も持っていない最初の 1 回は境界を 1 つも置かない: それがそのまま transcript の末尾の頁になる。`prev` が返らなければ、そこが transcript の始まり。

スクロール位置が「追う」と「読む」を分ける。末尾にいる人は起きていることを見ているので追記で view を動かし、それ以外の位置にいる人は読んでいるので動かさない。

**動かすのは本文のペイン** (`src/layout/scroller.ts`)。仮想化が要るのは「今どこを見ているか」「どれだけ見えているか」「どこまで伸びているか」の 3 つで、それをどの箱から読むかは算術の外側の話。読むのはペインにした — 頁を 1 本の scroll にすると、隣に並んでいる一覧も頁の長さを決めてしまい、一覧の方が長い日には「末尾」が本文の終わりではなく一覧の終わりになる。箱にするのはペインそのもので、その中の囲いではない: 内側に閉じた囲いは、その外の余白でホイールが効かず、窓の左右や上下の余白は画面の大半を占める。ペインは本文が使える所ぜんぶなので、余白ごと箱の中に入る。代わりに要るものは 2 つ: **話しかける所はペインの下に留まり** (`position: sticky`)、**探す窓は上に留まる**。どちらも遡った先で操作するものなので、本文と一緒に流れると、打つために末尾へ戻ることになる。

**錨はこちらが打ち、ブラウザのものは切る** (`overflow-anchor: none`)。ブラウザ自身の scroll anchoring は「見えている要素を掴んで位置を保つ」もので、掴んだ要素が DOM に残り続けることを当てにしている。仮想化では窓の外へ出た行はその場で消えるので、掴まれた先が消えて位置が飛ぶ。同じ役目のものが 2 つあって押し合うことにもなるので、切った上で下の錨を自分で打つ。

**戻る / 進むでは末尾から開く**。ブラウザの位置復元も掴む先の要素を要るので、描かれていない行に戻ることはできない。復元らしきものを自分で作れば「遡って読んでいた所」を再現できるが、それは追記で動き続ける transcript の上では**戻った時にはもう別の所**になる。ここでは末尾 = 今起きている所を、開き直しの既定にする。

**描くのは見えている所だけ** (`src/timeline/virtual-window.ts`)。持っている 1 MiB を全部 DOM に載せると、数行を読むために窓ぜんぶを描くことになる。DOM に載せるのは viewport とその上下 600px に掛かる group だけで、残りは上と下に積む 2 つの空白の高さになる (窓全体の長さをスクロールバーに持たせるためのもので、中身は無い)。覚えるのは**測った高さ**で、鍵は node の名前 = その先頭 item の id。測っていない行には**測った分の平均**を置く — 1 行に縮んだ道具呼び出しと畳まれていないコードブロックでは高さが桁で違うので、固定の見積もりでは空白の長さを外す。描く範囲を決め直すのは scroll のたびではなく**範囲が変わった時だけ**で、指の細かい動きで transcript を描き直さない。

**末尾に張り付いているか、1 行に錨を下ろしているかのどちらか**。追っている間は末尾が動くたびに末尾へ置き直す — 見積もりが実測に置き換わるたびに空白の高さが動くので、1 度置いて終わりにはできない。動いてもいないのに置き直さないのは、端とみなす数 px の中には末尾から離れようとしている指も居るから。読んでいる間は「最初に目に入っている行の名前と、その上端からのずれ」を覚え、遡って前に頁が足された時も、上に居る行の高さを測り直した時も、その行を同じ位置に置き直す。index ではなく名前で覚えるのは、窓が前にも後ろにも伸びるから (index は伸びるたびに別の行を指す)。窓が手放した行の高さは、その行に付いていた fold の開閉と同じ契機で忘れる。

**どのくらい前か、を配る時計は 1 本** (`src/now.ts`)。transcript には自分の古さを言う行が何百と並ぶので、行ごとにタイマーを持つと、見た目の変わらない描き直しが毎秒何度も走る。タイマーは 1 本にして、配るのは生の時刻ではなく**表示に出る粒度に丸めた時刻**を粒度ごとに 1 つずつ (10 秒 / 分 / 時 / 日)。行は自分の文が書かれている粒度だけを読む (`3m10s` なら 10 秒、`1h40m` なら分) ので、出ている文字が変わる時にしか描き直されない。閾値をまたいだ行は、自分の粒度の次の刻みで 1 段粗い方へ 1 度だけ移る。秒を 10 秒刻みにするのは、毎秒動く行が気を散らすだけで、transcript が答える問いが「どのくらい前か」であって「何時何分か」ではないから。粒度を読むのは**画面に出ている間だけ** (`IntersectionObserver`) — 長い transcript では出ていない行の方がずっと多く、そこで時計を読むのは誰も見ない描き直しにしかならない。

**描かれていない行にも既存の到達手段が届く**。数えるのが「持っているか」であって「今描かれているか」ではないのは畳まれた中と同じで、↑↓ での移動は、囲む fold を開くのと同じように、まず覚えている高さからその行の位置を出して窓ごとそこへ動かし、要素が出てから真ん中に寄せ直す。見積もりで動かした先にその行が居ることは、空白の高さと移動先が同じ高さの表から出ていることが保証する。

## 本文は窓より広くならない

読む幅は窓が決める。**横に伸びうるものは自分の中でスクロールさせ、外へは出さない**: コードブロックと表はそれぞれ自分の scroll 容器を持ち (`.md-code` / `.md-table-scroll`)、文は `overflow-wrap` で折る。

flex の中に置いた `<details>` には罠がある。開いた中身はブラウザが `::details-content` という箱に入れ、その箱が flex item として `min-width: auto` を持つ — 自動の最小幅は min-content なので、**中に 1 つでも折れないもの (表・長い 1 行) があると縮まず、親を押し広げる**。会話の吹き出しは名乗りと本文を横に並べていたためこれを踏んでいた。縦に積む形にして、本文が窓の幅をそのまま受け取るようにしてある — 名乗りの分の左余白が消えて本文が吹き出しの左端から始まるのは、同じ変更の表側。

遡って古い item が足された時にだけ崩れて見えるのは、押し広げるもの (表・コード) が手前の頁に居るからで、窓の計算とは別の話。だから基準は**狭い画面で遡った後**に置いてある (`test/visual/phone.visual.ts`): 絵と一緒に「窓より広い要素が 1 つも無いこと」を測る — 崩れた絵は「そういう見た目」と区別が付かないが、はみ出した要素の名前は誰が広げたかを言う。

## 色は語彙で、部品は名前だけを書く

部品の CSS が書いてよい色は **`app.css` の `:root` にある意味名だけ** (`--bg` /
`--surface` / `--border` / `--fg` / `--brand-*` / `--info-*` / `--success-*` /
`--warning-*` / `--danger-*` / `--member-*` / `--tag-*`)。生の hex も、混色も、半透明の作り置きも
書かない — 名前に無い色が要ると思ったら、まず語彙に足す (足せないなら、それは色で
なく別の手段で表す対象)。

段は**役割と 1 対 1**。`--surface` は「部品の地」で、`--surface-hover` は「触れて
いる間」、`--border-strong` は「押せることを示す枠」。同じ役割は色が違っても同じ形の
名前を取るので、「ここだけ中立を危険に差し替える」が名前の差し替えで書ける。

**誰が言ったかは色相**で言う。面も罫も文字も同じ 1 つの色相から段を変えて取るので
(`--member-*`)、1 行の色が揃って「1 人分」に見える。同じ人の弱い声 (思考) は色相を
保ったまま段が下がるだけ。型の違い (畳まれた答え、まだ渡っていない 1 通、通知) は
罫の形が言っていて、色相と混ざらない。

**その声がどれだけ重いかは色では言わない。** 声には 2 段あり、上の段はこのセッションと
人の 2 つだけ — 会話の主筋がそこにあり、残りは一段下がって字が小さく文字が弱くなる。
下の段の中は弱い順に**枠を減らす**: 思考は全周の破線 (同じ人が弱く言ったことなので
枠は減らさない)、別セッションから届いた 1 通は左の 1 本だけ、渡した先の声は枠を
持たない。枠の量が相手との遠さを言うので、色相を増やさずに並べられる。段を決めるのは
`voiceOf` で、誰かを決める `memberOf` とは別の関数 — 誰かと、その行が読む所かどうかは
違う問いだから。

人が選ぶ色相は 2 つだけ — 選択中セッションの **main** (`--h-main`) とユーザ。それ以外
の相手の色相は `src/member.ts` が配る。意味色 4 つと固定の 2 人の前後 15 度を避け、
**幅 30 度未満の隙間には配らず** (危険と注意の間は 16 度しか残らず、そこは琥珀に
見える)、相手の名前から作った希望が空いていればそこ、埋まっていればいちばん広い
空きの真ん中へ置き、**一度置いた色相は動かない** (増えるたびに色が動くと、色で人を
覚えられない)。名乗りが段 12、罫が段 8 なのは、
色相を機械が配る以上**円のどこでも**基準を満たす必要があるからで、それを
`test/color-contrast.test.ts` が 1 度刻みで見る。この 4 つだけは層 2 で唯一 `:root` の外
(`.member` の規則) に書く — custom property の中の `var()` は宣言した要素で解決される
ので、`:root` に置くと誰の行も `:root` の色相で解けてしまう。

見分けるためだけの色 (検索の帯、費用の系列) は意味色から借りず、独立した族
(`--tag-*`) から取る — 意味色を借りると、緑の系列が「正常」に見える。

値は**入力から算出される**。人が選ぶのは `app.css` の層 0 (主語の色の色相と色味、中立と意味色の色相、識別族の並び) だけで、12 段はそこから CSS の相対色構文で解ける — JS で色を計算しない。

読めることは**段表に閉じ込める**。文字は 4.5、境界として読ませる罫は 3.0 を満たす L を段表が持っていて、その検査は `test/color-contrast.test.ts` が `app.css` を読んで機械的に行う (比は CSS の式では書けない)。

段が持つのは**明るさだけ**で、light と dark は同じ 1 行に並ぶ
(`--step-9: light-dark(oklch(0.545 0 0), oklch(0.64 0 0))`)。色味は後から入力を載せる
ので、中立も意味色も同じ 12 段に乗る。どの face で立つかを述べる場所は
**`color-scheme` ただ 1 つ** — 述べていなければ `light dark` のまま OS が答え、
述べれば `:root[data-theme="light|dark"]` がそちらに固定する。この 2 規則は色の値を
1 つも持たない。

**選ぶことと見ることは 1 つ。** 色相を動かしても、それがどこに出るかが見えなければ
良し悪しの言いようが無いので、入力の隣に**表示例**が並ぶ — 吹き出し (main / ユーザ /
他の相手 / 思考 / 通知)、押せるもの、行、意味の色 (面と塗りの両方)、識別の族、繋がりの
点、コード。どれも実物の部品で、値を流し込む経路は持たない (同じ `:root` を読んで
いるので、入力が書き換われば一緒に解け直す)。

選ぶのは設定の画面 (`/settings`) の中の**色の section**で、**基本と詳細の 2 段**になっている。基本に出るのは face と色相 3 つ (主語の色・自分・ユーザ) だけで、残りは既定のまま導かれる。詳細は畳んであり、開くと**残りの入力** (中立の色味、意味色 4 つの色相、識別の族) が並ぶ。同じ入力を両方に出さないのは、同じ値を動かす操作子が 2 つ並ぶと読み上げる人に区別が付かないから。出ているのは層 0 の入力と face だけで、段表は出てこない — 読めることはそちらに閉じ込めてあり、人が選ぶ側には置かない。

主語の色はカラーピッカーで選ばせ、**色相と色味の 2 つ**として覚える (明るさは段が
決めるから)。選ばれた色からその 2 つを取り出すのは相対色構文でブラウザにやらせて
いて、ここに変換の計算は無い。

名前付きの組 (標準 / 暖色 / 寒色 / 無彩) は層 0 の入力だけを配るもので、段表を持たないから、どれを選んでも読めることは崩れない。組は face を持たない — 段が face ごとの明るさを 1 行で持っているので、1 つの組が既に両方の姿を持っている。

**今のブラウザにあるものを使う。昔からの書き方に回らない。** 対象は**最新の Chrome
と最新の Safari の 2 つだけ** (Firefox も古い版も保証しない) なので、機能はその 2 つで
使えることを実測した時点で採る — Baseline の Widely available までは待たない。色の
体系が乗っているのは `light-dark()`・相対色構文・`oklch()`・`color-scheme`。

なぜそう決めたか、何を採り何を採らなかったか、何を実測したかは
[DR-0001](decisions/DR-0001-colour-is-computed-from-a-few-inputs.md)。決め方の全体
(入力・段・算出・検査・ブラウザ対応) は `docs/design/color-system.md`。

## 設定は section の集合で、触ることと決めることを分ける

設定は **section の集合**で、section は入力の組。今あるのは色 1 つで、次に来るのはレイアウト・語・フォント・部品の大きさ・timeline に出す項目あたり — どれも「この端末でどう読みたいか」で、instance が言っていることではない。だからこの画面は **instance に何も聞かない**。繋がっていなくても、サインインしていなくても立つ。

**触ることは試すこと**で、覚えるのは「保存」を押した時だけ。離れるか読み込み直せば覚えてあるものに戻るので、見比べるために動かした値が残らない。値は 3 つの姿で持つ — 覚えてある値、今画面に出ている下書き、そして**比べる先** (組を選べばその組、選んでいなければ覚えてある値)。ベースと違う項には印が付き、項ごとに戻せる。差の判定は 1 か所にしかなく、行に印を出すかはその行の「戻す」が押せるかを CSS が `:has()` で読んで決める。

覚える所は `ccmsg.settings` の **1 つの文書**で、section ごとの部分をその名前で持つ。鍵が section の数だけ増えると、消すのも移すのも section の一覧を知っている誰かが要る。

section が言うのは「何が入力か」「どう覚えるか」「どう画面に効くか」「2 つの値のどこが違うか」だけ。組・差の印・「戻す」・保存は section を問わない仕組みと部品が持つ。次の section を足す時に触るのは、section の定義とその入力を描く部品と、画面の並びへの 1 行。

なぜそう決めたか、何を捨てたかは [DR-0002](decisions/DR-0002-settings-are-sections-tried-before-they-are-kept.md)。

## 操作はアクションで、区画が宛先になる

押す所と打鍵は**同じ 1 つのアクション**を起こす (`src/actions/`)。アクションが持つのは id と題と、危ないものに付く印だけ (`catalogue.ts`) — 実装は 1 つも持たない。「今できるか」と「実行」は**スコープの側が名乗り出て**持つので、同じ id を場所ごとに別の担当が持てる。人が覚えるのは「次へ」「探す」の 1 語で、それが今どこに当たるかは宛先が決める。

**スコープの木は部品の木そのもの**。区画になる部品が `<Pane name="tl.body">` と名乗り、入れ子がそのまま親子になる (`src/ui/Scope.tsx`)。図を別に持たないのは、ずれるのがいつも図の側で、しかもずれても何も壊れないから。版組を持たない節 (`Holder`) もあり、一覧の 1 行がそれ — 行の中の押す所は**その行**を対象にした担当に当たり、打鍵は区画から登るので**カーソルの行**を対象にした担当に当たる。同じ id、同じ題、違う担当。

**立っている区画はアプリの状態が正**で、DOM のフォーカスではない。この画面ではフォーカスの外れ方が多すぎる (余白のクリック、埋め込んだ端末、`autoFocus` の入力)。フォーカスが効くのは「文字を打っている最中か」の判定だけで、入力欄に居る間、打鍵はどのアクションにも回らない。向きは**状態 → DOM の一方向**: 立った節へ focus を移すのは、読み上げに「今どの区画か」を伝えるのが focus だけだから。区画の中では roving tabindex で、tab が届くのはカーソルの行だけ。

起動は**内側から外へ登り**、担当が見つかった所で止まる。担当はするが今できない時は上へ流す — TL に選択中の 1 通が無くて「次へ」が効かないなら、外側の一覧の「次へ」が動く方が望みに近い。流れると困るものは `destructive` の印で括り、印付きは無効時にそこで止まる。担当が 1 つも見つからなければ**何もしない** (`preventDefault` しない) ので、ブラウザの標準の手は残る。

危ないアクションの責務は**確認を開くまで**。実際に終わらせるのは確認の中の決定で、キーから起こしても押す所から起こしても同じ 1 つのアクションを通るから、確認の出ない経路ができない。確認は木の節を 1 つ持つ区画で、開いた時点でそこが立っている区画になり、閉じれば宛先は元の区画へ戻る。

宛先の区画には**細い縁**が付く。色は focus ring と同じ意味名 — 「今ここがキーを受ける」という意味は 1 つなので、区画の縁と要素の ring で別の色を持つ理由が無い。

区画が自分の役として持っている打鍵は、設定のキーの表とは別物。一覧の上下・決定で開く、tl 本体の上下と PageUp / PageDown、区画ごとの `/` — どれも「一覧なら上下で辿れる」という区画の役で、`separator` が ← → で動くのと同じ所に居る (部品の中で閉じる操作なので表には載らない)。一覧の **← は「1 つ外へ」の 1 語**で、セッションの上ならそのセクションの見出しへ、見出しの上なら畳む。人が結んだ表の方が先に引かれるので、上下を別のことに使いたい人が区画の役に阻まれることはない。

今の platform は、`userAgentData.platform` と `navigator.platform` の**どちらかが mac だと言えば mac**。食い違う環境が実在する (自動化された Chromium は macOS の上でも前者に `Windows` を返す) 上に、mac を mac でないと読むと `CmdOrCtrl` が Control に解決して、⌘ のつもりの割り当てが効かないまま Control 側を奪う。

**「できるか」が読んでよいのは signal だけ**。押す所はそれを描画の中で問うので、signal 以外を読むと「押せるようになったこと」を伝える相手が居ない (props が同じままの押す所は描き直されない)。

platform の道具は、自前で書かずに済む所で採る。確認は `<dialog>` の `showModal()` — 後ろが不活になるのも、`Escape` で閉じるのも、トップレイヤに出るのもこれ 1 つに付いてくるので、`inert` を自分で貼らない。セクションの畳みの印は CSS の `content` で出す (見出しの**文字**は見出しの名前だけにしておくと、読む所も読み上げも印を読まない)。**Invoker Commands (`command` / `commandfor`) は採らなかった** — 押す所が起こす先を属性で名乗る形は合うが、`commandfor` が指すのは**要素**で、ここで要るのは「立っている区画から登って担当を探す」解決。押せるかと題もアクションから読むので、結局 JS を通る。

なぜそう決めたか、何を捨てたかは [DR-0003](decisions/DR-0003-an-action-is-what-a-key-and-a-button-both-reach.md)。

## キーバインドは設定の 1 section

キーの表は設定の section 1 つ (`src/actions/keys.ts`) で、値は**打鍵の綴り → アクション id**。表はアクションの実体を知らないので、この画面が知らない id が表に残っていても、その行が効かないだけで済む。設定の画面に並ぶのは**アクションの一覧**の方 — 人が探すのは「これを打鍵でやりたい」であって「この打鍵は何だったか」ではないので、題と id はアクションの側から自動で並ぶ。

同じ打鍵が 3 つの姿を持つ。**保存する意味は `{ code, modifiers }`** で、`code` は `KeyboardEvent.code` (配列に左右されない物理位置)、修飾子は集合なので順序と重複がそこで正規化される。**人が書く綴りは `CmdOrCtrl` / `Cmd` / `Ctrl` / `Alt` / `Shift`**。`CmdOrCtrl` は今の platform の主要な修飾子**1 つに解決する**置き換えで、論理和ではない — mac の Control は端末の制御文字・Emacs 系の手・VoiceOver が使っているので、両方で発火させるとそれらを巻き込んで奪う。**画面に見せる表記**は platform に解決した後の姿 (mac は `⌘⇧K` と記号を繋げ、それ以外は `Ctrl+Shift+K` と語を `+` で結ぶ)。設定の入力欄には綴りをそのまま置き、隣に解決結果を添える — 記号だけでは転記できず、綴りだけではどのキーか分からず、添えた結果が「置き換えである」ことを目に見せる。

binding は **platform を限定できる**。限定が要るのは「キーが無いから」ではない — 押せるかは物理キーの有無で決まり、無いキーは押されないので限定も要らない。要るのは**同じキーが両方にあって、ブラウザ側の扱いだけが違う場合**で、`Ctrl+F` がそれ (Windows ではブラウザの検索、mac では空き)。限定は衝突の検査より先に効くので、`Ctrl+F` を mac だけに結べば ⌘F とは被らずに通り、他の platform ではその行がそもそも無い。

ブラウザの手と被る組み合わせは **禁止せず、2 種に分ける**。**警告**は奪えてしまうもので、何が失われるかを言った上で `force` を付ければ通る (自分のブラウザで ⌘F を使わない人から、こちらの都合でその組み合わせを取り上げる理由が無い)。**予約**はブラウザがページに keydown を渡さないもので、`force` を付けても効かない — 断るのではなく、**設定できても効かないことを表示する**。割り当てたのに何も起きない時、それが書き間違いなのかブラウザの仕業なのかは、画面に出ていなければ人には分からない。予約の一覧の出所は **Chromium のソース** (`IsReservedCommandOrKey` と accelerator 表) で、Safari は本体が非公開なので公開のショートカット一覧とメニュー定義に、ページへ渡るかの最小限の観測を足してある (DR-0003 §2.5)。片方のブラウザでも届かないなら予約として扱う。

**変換中の打鍵はどのアクションにも流さない。** `isComposing` と `keyCode === 229` を捨て、Safari が確定の Enter を `compositionend` の後に `isComposing: false` で配ることに合わせて、その直後 1 回の Enter / Escape も確定の側に数える。門は画面ぜんぶで 1 つ (`src/actions/ime.ts`) で、入力欄の中で閉じる操作 (送る) も同じものを引く — 1 人目で印を消すと 2 人目には確定の打鍵が本物に見えるので、同じ打鍵には同じ答えを返す。

## 部品の階層と、それぞれが持つもの

差し替えたい所が 1 か所で済むように、階層ごとに**持つもの / 持たないもの**を
決めてある。迷ったら「これが変わった時に触るのはどの階層か」で決める。

| 部品 | 持つもの | 持たないもの |
|---|---|---|
| `App` | 姿 (`phase`) を読んで選ぶこと | 姿を決めること (= `src/phase.ts`)、並べ方・画面・読み方 |
| `Shell` | 接続後の並べ方 (道・通知・2 ペイン・フッタ) | どの画面か、何を読むか |
| `ConnectionBar` | **接続前の**住所と接続 | 一覧や本文の中身、他の画面への入口 |
| `GlobalNav` | 接続後の他の画面への道と、状態の印と読み込み直し | 接続の詳しい中身 (= アカウントの画面) |
| `Panes` (`Shell` の中) | 2 ペインの配置、境目の幅の覚え、狭い画面の滑り | 中身が何であるか |
| `Splitter` | 掴む・キーで動かす・覚えた幅の読み書き | 何と何の境目かという意味 (名前と鍵は渡される) |
| `Pane` | 木の節を名乗ること、立っている時の縁、focus の追従 | 中身が何であるか、どのアクションがあるか |
| `Act` | アクションを起こす 1 行と、押せるか・題をアクションから読むこと | することの中身 |
| `Confirm` | 危ないアクションの確認を区画として立てること | 何を確認するか (アクションが渡す) |
| `SessionList` | セッションの一覧と、行の上の操作 | 本文の画面、レイアウト |
| `Main` | **URL → 画面**の対応 | 画面が何を読むか、レイアウト |
| 各画面 (`Timeline` / `Files` / `Status` / `Usage` / `TerminalPanel`) | その画面が読むもの (topic / op) と、その描き方 | 自分がどこに置かれているか |
| `Settings` | section の一覧と、その入力 | instance が言うこと一切 — 何も読まないが、**入口は接続後にしかない** (下記「姿」) |

**一覧は「まだ聞いていない」と「何も無い」を区別する。** セッションの一覧と端末の一覧は別々に届き、起動しただけでまだ名乗っていないハーネスの行は後者からしか出てこない。どちらも受け取るまでは空の一覧を「セッションはまだありません」と言わず、聞いている最中だと言う。受け取り切ったことは区画にも出る (`data-settled`) — 中身が届く途中かどうかは状態からしか分からないので、絵を撮る道具もそこを読む。

## 一覧と本文は並んでいて、狭い所では並ばない

画面は上の道 (`GlobalNav`) と、その下の 2 ペイン。左が一覧、右が URL の
名指すもので、境目は掴んで動かせる (`src/ui/Splitter.tsx` — ファイルの木と本文で
使っているものと同じ部品。違うのは名前と、覚える鍵だけ)。

**本文の幅に上限を置かない**。広い机では広く、狭い端末では狭く読む — 上限を置く
ことは「この画面の正しい読み幅はこれだ」という主張で、それは読む人が決めること。

2 枚はどちらも窓の高さを持ち、**縦は別々に動く**。1 本の scroll を分け合うと、長い方が短い方の高さまで決めてしまう — 一覧が長い日には、本文の「末尾」が本文の終わりではなく一覧の終わりになる。

狭い画面では**並べない**。2 枚は横に並んだまま、見ている方へ滑らせる (90ms、
どちらへ動いたかが見える最短)。どちらを見ているかを決めるのは **URL** で、一覧に
居れば一覧、セッションに居れば本文 — 画面の状態をもう 1 つ増やさずに済む。

道の「一覧」は幅で意味が変わる。並べている画面では左のペインを畳む / 出す、
並べていない画面では一覧へ戻る道。**どちらかは CSS が正本** (幅の境目は 1 か所に
持ち、押した瞬間に読む)。畳んだかどうかと境目の位置は localStorage に残る —
前者はこのブラウザの好み、後者は instance ごと (相手によって欲しい広さが違う)。

## 画面ぜんぶの姿は 1 つの値が決める

どの姿で立つかを答えるのは `phase` 1 本 (DR-0004)。規則は `src/phase.ts` の `phaseOf` で、材料 (signal) を渡す 1 行が `src/state.ts` に立っている。`App` はその答えを `switch` するだけで、**他のどの部品も姿を決めない** — 決める所が 2 つあると、順番や優先が誰も点検していない裁定を作る。「読まないこと」は文章ではなく test が守る (`test/phase.test.ts` が `src/ui/` を走査する)。

| 姿 | 何か | 木の根 |
|---|---|---|
| `offline` | 住所を述べる所があり、繋いでいない | 未接続 |
| `registering` | 登録 URL を開いた | 未接続 |
| `authenticating` | passkey を求める所に居る | 未接続 |
| `connecting` | socket を開けている (名乗りの途中も含む) | 未接続 |
| `receiving` | socket は開いた、一覧の snapshot がまだ | 未接続 |
| `live` | 一覧があり、話し相手が居る | 接続後 |
| `stale` | 一覧があり、話し相手が居ない | 接続後 |

**「未接続」は「一覧がまだ立っていない」の意**で、回線の有無ではない。

**接続前の主役は接続バー**で、住所と「接続」しか持たない。設定もアカウントも使用量もそこには無い — 繋ぐ前の人に出す道は、出した分だけ「繋ぐ」以外の道を増やす。**接続後は帯を持たない**: 他の画面への道は `GlobalNav`、繋いでいる先は下端のフッタに極小で、接続状態は道の中の印 1 つになる。instance・daemon の版・契約世代・誰として・この接続の期限は**アカウントの画面**が持つ (常に出しておくと、ほとんどの時間なにも決めない文字列が画面の幅を取り続ける)。

**読み込み直しはどの姿にも常に居る**。ホーム画面に追加した PWA にはブラウザの再読み込みが無いので、これが無いと読み込み直す手段を持たない端末ができる。**契約の世代が食い違ったら、このボタンの色が変わる** — 帯も自動の読み込み直しも持たない。画面に出ているものを、この画面の判断で隠したり捨てたりしないため。

**`stale` で画面も URL も保つ**。回線が切れただけなら退がりながら繋ぎ直し (refresh が届かない `unreachable` もこちら — 届かないことは許可が切れたことではない)、向こうが断った時 (`auth_invalid`) だけ、画面の中央に passkey の再認証を重ねる。通ればその場で繋ぎ直り、後ろの workspace は最初から動かない。**その頼みは閉じられる**: `stale` は読める姿なので、閉じられない重なりは後ろを不活のままにして切断も読み込み直しも押せなくする。閉じても許可が切れている事実は下りず、状態の印がそのまま頼みを出し直す入口になる。**重ねた再認証を断られても画面は捨てない** — 取り消したのは「今はやらない」であって、読んでいたものを捨ててよいという意思ではない。

**未接続で接続後の URL に来たら、まず繋ぎに行く**。繋げたらその URL の画面で、繋げない時に URL を `/` へ戻すのは**憶えた住所が無い端末だけ** (`ccmsg.endpoint` が判定) — そこはまだ誰のものでもない。憶えた住所がある端末では、回線が届かなくても refresh token が切れていても URL も画面もそのままにする。受け取ったリンクが一度の通信の失敗で失われるのは高く付く。

## 切断は 3 つあり、3 つとも別のことをする

画面に出る行は全て **instance が今そう言っていること**なので、切断に何をするかは
「何を失うか」の判断になる。3 つに分ける。

| 切断 | 画面 |
|---|---|
| **まだ一度も聞いていない** (初回・未接続) | 一覧も transcript も mesh の行も描かない。本文は空で、状態を言うのも繋ぐ手も接続バー 1 つ (`src/ui/Disconnected.tsx`) |
| **意図しない切断** (回線断、instance 側の終了) | 聞いたものはそのまま出したままで、古いことを道の中の印が言う。次の snapshot が同じ行を置き換える |
| **人が押した切断** | メモリに持っているものを全部捨て、向こうに失効を頼み、`ccmsg.` の付くこの origin のキーを消して頁を立て直す (= この端末から降りる)。戻るには passkey からやり直す |

**画面に出す切り方は 1 つ** (DR-0004 §2.6)。このシステムは接続 = 認証なので、繋がっていない状態と降りている状態を人が区別する意味が無く、webui の操作は「切断」1 つ = この端末から降りること。契約の `auth.signout` で token family を失効させ (cookie は HttpOnly なので、期限切れにできるのは向こうの応答だけ)、`ccmsg.` の付くこの origin のキーを**既定で 1 つ残らず消す**。残したい人のために設定を 1 項持つが (既定 off)、残るのは人の好みだけ (下記「localStorage のキー規律」)。**向こうが答えなくても手元は消す** — 降りると決めた人の端末に跡が残る方が悪く、届かなかったことは 1 行の言葉にして残す。**最後にトップを読み込み直して終わる**: 跡が残らないとはメモリに持っている写しごと消えることで、読み込み直せば消して回る一覧を別に持たずに済む (好みが戻るのは残す設定を入れた時だけで、それは localStorage に残ったものを読み直した結果)。届かなかった 1 行は URL の fragment で次の読み込みへ渡り、読んだ所で URL から消える。socket を閉じるだけの切り方を別に並べないのは、語の違いから結果の違いを読み取れないまま片方が「跡が残る切り方」になるから — 席を外すだけなら頁を閉じれば済み、cookie が残って困るのは降りたい人の方。取り返しが付かない側なので、押したら一度確かめ、道には常時出さずハンバーガーの中に畳む。**意図しない切断はこの操作ではない** (回線が落ちただけなら印が言い、認証が切れていれば再認証の頼みが重なる)。

本文に説明も 2 つ目のボタンも置かない。繋がっていないことも、繋ぐ手も、接続バーが
既に持っている — 押す所を 2 つに増やすと、どちらが本物かを読む人が考えることに
なる。本文に残るのは、この画面では登録できない登録 URL を開いた時の 1 行だけ (黙って
いると「押したのに何も起きなかった」になる)。契約の世代の食い違いはそこに出ない
— 常設の読み込み直しの色が言う。

聞く前に枠だけ描かないのは、それが**空の一覧**になるから — 行が 0 件の一覧は
「セッションが 1 つも無い」であって「繋がっていない」ではない。だから出るのは
繋がった瞬間ではなく**一覧の snapshot が届いてから** (`listed`)。socket が開いた
時点ではまだ何も聞いていない。

逆に、切れただけで画面まで空にしない。持ち歩いて読む道具で、電波の切れ目ごとに
読んでいたものが消えるのは失いすぎで、次の snapshot が上書きするまでの間、最後に
聞いた内容には読む価値がある。**いつのものかは行に書いていない**ので、それは道の中の印が
言う。捨てるのはそこで意味を失うものだけ — 接続の期限、「今それが起きた」という
通知、届かないまま消えた 1 通の控え。

人が押した切断だけが持ち物を捨てる。切れただけで持ち物まで消えるなら、電波の悪い
所を歩いた人は毎回ログインし直すことになる。

## 訳は 2 つ並べる。1 つに混ぜない

英語の本文を日本語で読む道は 2 つある — このブラウザが持っている翻訳機
(`Translator`) と、instance の host が持っている翻訳機 (`translate.run`、能力
`translate`)。**どちらも残し、選択肢として並べる**。

混ぜないのは、2 つが違う道具で違う文を出すから。片方は辞書寄りで、もう片方は
言い換えを作る。1 つの「訳」に畳むと、おかしな 1 文に出会った時に**どの道具の
仕業か**が消える — 訳を読む人がまず知りたいのはそこで、それは選択肢の名前
(`日本語 (host)` / `日本語 (browser)`) がそのまま答えている。使える道具が 1 つも
無ければ選択肢自体を出さない (押せないものを並べない)。

選ぶのは画面に 1 つ。英語の transcript を読む人は「日本語で読む」と 1 度決める
のであって、item ごとに決め直したいわけではない。訳が走るのは**窓が描いている
item だけ**なので、遡って読んでいない何百もの item を訳しに行くことはない。

**入口は読んでいる所にも置く**。設定は 1 つでも、押す場所は 1 つでは足りない —
transcript の上端にしか無いと、末尾を読んでいる人は上端まで戻ってから押すことに
なり、戻った時点で読んでいた所を見失う。だから item の文にも小さな入口を出し、
押すと画面ぜんぶの設定が動く (その item だけが訳される設定ではない)。入口が出る
のは**訳す所を持っている文だけ**で、日本語だけの文には出さない — 押して何も
変わらないものが並ぶと、どれを押せば変わるのかが読めなくなる。

切り替えで読んでいる行が動かないのは、TL が自前で錨を打っているから (`remember` /
`place`)。訳で高さが変わっても、最初に目に入っている行を同じ高さに置き直す。

訳すのは **item の文だけ**で、道具の引数も囲みコードも通さない。訳して意味が
変わらないのは散文だけで、識別子やパスは訳された瞬間に別のものを指す。だから
本文は段落で切る前に**囲み (``` / ~~~) で切り**、囲みは中の空行ごと 1 つの塊と
して訳しに回さない。塊は後ろの区切りごと持つので、繋ぎ直せば訳さなかった所は
1 文字も動かない。

段落ごとに訳し、**届いた段落から出す**。長い思考を丸ごと待つと数十秒何も変わら
ないので、訳せた段落から順に入れ替え、まだの段落は原文のまま並ぶ。訳せなかった
段落も原文のまま残る — 1 段落の失敗で本文ぜんぶが読めなくなる方が悪い。失敗は
覚えないので、helper が戻れば次に開いた時にもう 1 度試す。

もう日本語の段落は訳しに回さない。判定は**比率**で、日本語の文字が 1 割を超える
段落は日本語とみなす。「1 文字でも日本語なら訳さない」だと、英文の思考に人の
言葉が一言引用されただけで段落ぜんぶが英語のまま残る。

## 書き出しは file を残すことに値打ちがある (試作)

transcript を 1 つの file に書き出す入口を、状態の画面に足してある。選ぶのは
**献立の名前だけ** — 範囲や型の選択も契約は受けるが、まずは「後で誰かに渡せる
file を 1 つ作る」に絞る (使って足りない所が分かってから足す方が、要らない欄を
先に並べるより小さい)。献立の名前を列挙できる op はこれしか無いので、名前は
instance に聞く (自由入力にして断らせない)。

書くのは **instance の host** で、画面が出すのはその場所と、何をどれだけ書いたか。
中身は運ばない — 読むだけなら transcript の画面があり、この op の値打ちは「後で
渡せる file がそこに残る」ことの側にある。

## 行の上でできること (試作)

一覧の行に 3 つだけ足してある。新しい画面も新しい形も作らず、行の中で完結させる
— 使ってみてから要る / 要らないを決める前提の試作なので、部品を増やさない。

- **留める**: このブラウザの覚え (localStorage) で、instance には送らない。「今
  追いかけている仕事」は人ごとに違い、同じ instance を見ている他の人の一覧を
  動かす理由が無い。留めた行は、どの並びを選んでいても先に来る
- **改名**: 名前がその場で入力欄になる。instance は端末にそのセッション自身の
  改名コマンドを打つので、成功は「打鍵が届いた」であって「名前が変わった」では
  ない (変わった名前は後から `agents` topic で届く)。端末を前に置いていない
  instance では出さない (`terminal` の能力)
- **終了**: 押すと確認が開く。実際に頼むのは確認の中の決定で、**消えなかった
  時だけ**強い方が行に出る — 強い方は transcript を書き切る機会ごと奪うので、
  画面が自分で選ばず人が決める (契約が `force` をそう定めている)。確認は区画
  ひとつなので、キーから起こしても同じ段を通る (上記)

## セッションと run は別のもの

セッションは transcript と畳んだ状態、run はそれを走らせている 1 プロセス (契約 DR-0001)。URL がどちらを見ているかを言う: `/s/<sid>` はセッション、`/s/<sid>.<pid>` はその 1 run。

**行がどこに立つかは行から読む** — 契約の `liveness` / `reachable` / `waiting`。どの見出しに入るかを線が言うことはない: 言葉はこの画面のもの、算術は契約のもので、instance とこの build が同じ行を 2 通りに見せることが無い。2 つのプロセスが書いているセッションが一覧の先頭に立つのは、それが別の問い (プロセスが何個あるか) の答えだから — 人がどちらかを選ぶまで、その行について他のことを読む意味が無い。**見出しはセクションの名前をそのまま出す** (`Duplicated` / `Waiting` / `Live` / `Unreachable` / `Paused` / `Disappeared`): 状態の名前は契約とこの画面が共有している語彙で、訳すと画面と会話で同じものが別名になる。並びは手が要るものから要らないものへ下る。**まだ名乗っていないハーネス** (`起動中`) はその後ろ — 出来ることは端末を覗くことだけで、一覧の中でいちばん手が少ない。

**2 つのプロセスが書いているセッションは、セッションとしては出さない**。畳みは凍り、送る・書き出す・ファイルを読むは断られる (`session_duplicated`)。なので着く画面は run の並びと、run ごとに言えること (pid・起動・接続の有無・端末・何を待っているか) だけにする。断られるものは描かない — 押したら断られる入力欄は、無いより悪い。run を選ぶと `/s/<sid>.<pid>` に行き、同じ材料と、そこで唯一できること (**その run を pid で名指して終わらせる**) が出る。sid だけでは instance がどのプロセスか決められないので、pid を名乗る。

**もう無い run は、無いと言う**。そのセッションの run に無い pid は、黙ってセッションを出すのではなく「終了した」と言う — 番号は OS が配り直すもので、リンクは 1 プロセスについて作られたものだから。run が 1 つしか無いのに run を名指した URL は、制限する理由がもう無いのでその旨を言ってセッションへ渡す。

**畳みが何を言えるかは、畳みを読む所すべてに出す** (`session_status`): `absent` は 1 行も読んでいない、`folding` は途中まで、`frozen` は止める前に信じられた最後の値。途中の畳みを全部であるかのように描くと、「このセッションには何も無い」と言ってしまう。

**ハーネスが起動しただけで、まだセッションを名乗っていないもの**は、セッションの一覧ではなく**端末の側**から見える (契約 DR-0026 の `starting`)。id が無いので行は何も開かず、端末だけを出す。

## 費用は日ごとの記録を、読む単位に畳む

gateway が持っているのは**日ごと**の記録で、画面はそれを日 / 週 / 月に畳んで
出す (`src/llm/stats-view.ts`)。週は ISO の週番号にする — 「今日から 7 日前まで」
だと、同じ「先週」が開く日によって別の範囲を指し、先週と今週を比べられない。

1 日の合計は **gateway 自身の数字が勝つ**。model ごとに割れない分まで数えた正本
なので、内訳の合計を上回ることが正当にありうる。言っていない日だけ内訳を足して
埋める。

単位を変えたら聞き直す。束ね方だけ変えても、月別を埋めるには日ごとの記録がもっと
要るから — 聞く日数は描く幅より少し広く取り、いちばん古い束を途中で切らない。

棒は model で積む。高さの基準は**その画面でいちばん高い束**で、絶対額に固定
しない (比べたいのは束の間の差で、安い週が潰れて読めなくなる方が損)。図の
library は入れない — 描くものが棒と区切りしか無いなら、読む人が見る形をその
まま書く方が小さい。

## 型ごとの表示属性

**どの item をどこに、どこまで開いて出すかは型が決める** (`src/timeline/display.ts`)。軸は 2 つだけ:

- **トップ** — TL のトップ層に立つか。立たない item は、続いた分がまとめて 1 つの畳み (`N item`) に入る
- **開く** — 既定で開いているか。畳みに入る item では囲む畳みが開くかを決め、本文を持つ item (会話・思考) ではその本文が開いているかを決める

**表は主語ごとに 2 面持つ** (`main` / `sub`)。同じ `tool.Bash` でも、main では会話の傍らで起きたことで、worker ではその worker が**やったこと**そのもの — 読む理由が違うものに 1 つの既定を押し付けない。組み込み既定も 2 面で、main は会話と思考が本文ごと立ち道具は畳みの中、sub は道具をトップ層に 1 行ずつ並べて本文は閉じる (worker を開くのは何を叩いて何を読んだかを追うためで、本文まで開くと 1 件で画面が埋まって順番が読めない)。どちらの面が効くかは**開いている transcript の主語**が決める (sid だけなら main、agent を名指していれば sub)。継ぎ方は面の中で閉じていて、面をまたいで継ぐことはない。

**設定は型名の階層で継ぐ**。型名は `.` 区切りなので、`tool` に付けた値は `tool.Bash` にも効き、`tool.Bash` に付けた値がその 1 つだけを上書きする。何も付いていない型は組み込みの既定に落ちる。**軸ごとに独立して付く**ので、`tool` の既定を継いだまま `tool.Bash` の片方だけを動かせる。型は harness が増やし続ける開いた集合なので、平らな一覧では知らない型に何も言えない — 階層なら「その根が言っていること」が必ず答えになる。

**値は面ごとに覚える** (`ccmsg.timeline.display:<main|sub>`)。「思考は畳む」のような決め方は読み手の都合なので、instance でもセッションでも分けない (下記「localStorage のキー規律」)。壊れた値は entry 単位で捨てる: 1 つの型の値が読めなかったことで、他の型に付けた値まで失う理由が無い。

**設定画面は今の主語の面を開き、もう一面はタブで切り替える**。worker の読み方を、worker を開く前に決められるように。並ぶのは、組み込みが名乗っている型と、その画面で実際に見た型 (とその上の型)。見ていない型を先回りで並べても、その instance が出さない型の行になる。継いでいる値は薄く出し、押せばその型に付き、「継ぐ」で外せばまた上の型か組み込みが答える。

## worker を主語にして開く

親の transcript に出るのは worker への指示と返ってきた答えだけで、**その worker が何を叩いて何を読んだかは worker 自身の transcript にしかない**。`/s/<sid>/agent/<agentId>/timeline` がその 1 つを主語にして開く。

**読むのは `transcript.items.read` に `agent_id` を添えるだけ**で、item の型も範囲の切り方も session を読む時と同じ。型は主語相対に定義されているので (`message.user.in` は worker では親からの指示書)、同じ語彙のまま主語だけが移る。生 record も `transcript.read` の `agent_id` で同じように引ける。

**追記は追わない**。追記を運ぶ topic は `transcript.items:<sid>` で、これは**セッションのもの**。worker の追記を運ぶ topic は契約に無いので、worker の画面は購読を立てず読むだけにする (立てると親の transcript が worker の画面に混ざる)。続きは読み直すと出る、と画面に書く。

**agent の下にあるのは timeline だけ**。ファイルも端末も状態もセッションのもので、worker に自分のものは無い。別のタブ名を書いた URL は timeline に落とさず 404 にする — 黙って落とすと、送られてきた link が何を指していたかが分からなくなる。

**導線は往復で置く**。`message.sub.out` / `message.sub.in` / `tool.Agent` の行に `agent_id` があれば「この worker を開く」を出し、worker の画面には親へ戻る所を出す。id がどちらの item に書かれていたかは関心ではないので、行の呼び出し側と答えの両方を見る。

## 描画層: Markdown とハイライト

agent が書いた text は **Markdown として読む**。mdast (`mdast-util-from-markdown` + GFM 拡張) の木を JSX へ手で歩き、HTML 文字列の段を一切通さない。`innerHTML` / `dangerouslySetInnerHTML` は使わないので、`<` や `&` を含む本文の逃がしは Preact のテキストノードがそのまま担う。

**人が打った text は別の読み方をする** (restricted)。`#3 の件` は見出しではないし `<R G B>` は HTML タグでもない。人が意図して使うのは inline code・fenced code・引用行の 3 つだけなので、restricted はその 3 つだけを解釈し、残りは打たれた文字のまま出す。mdast を歩いてから plain へ戻すのではなく source を直接字句解析するのは、木を経由すると元の文字 (`#` の有無、`_foo_` の空白) が復元できなくなるため。

**link の宛先は 3 通りにしか落ちない**。http/https/mailto は別タブ、`#fragment` と自分の origin を指す絶対 URL は同じタブ、それ以外 (`javascript:` 等の scheme、およびファイルパス形) は **`<a>` を出さない**。パス形を origin 相対の `href` にすると、このページを配っている origin へ遷移して戻る手段が無くなる (address bar の無い standalone PWA では復帰不能)。画像も同じ判定を通し、`<img src>` で自動取得はしない — 描画しただけで閲覧者の IP/UA が第三者に届くため、alt とリンクだけを出して人が選べるようにする。

コードのハイライトは Shiki を**遅延 chunk** で読む。engine と grammar は `getHighlighter` の中の `await import()` で取るので、コードの無いセッションは 1 つも取得しない。言語表と大きさの閾値だけは先に載っていて、これが「ハイライトするか」を highlighter を払わずに決められる根拠になっている。token は light/dark を同時に持たされ、どちらを使うかは CSS が決める (theme ごとの再 tokenize をしない)。

## fold の開閉

fold の開閉状態は fold を描く component の**外**に置く (`src/timeline/fold-open.ts`)。窓が動けば component は unmount されるが、そこで開閉が戻るのは「アプリが忘れた」と読める。

**key ごとに signal を 1 本**持ち、map を持つ signal 1 本にはしない。component は自分が描く key を読むので、1 つ開いても timeline の残りは再描画されない — 状態を外に出した理由そのもの。

**触られた fold だけ**を記録する。無い = 呼び出し側の既定のまま、という意味で、これが型ごとの表示属性の変更を、store が各 fold の既定を知らないまま効かせる方法になる (設定変更 = override を捨てる)。

**閉じた fold の中身は描かない。ただし一度開いたら描き続ける**。transcript の大半は fold の中にいるので、閉じた中身まで描くと数行読むためにセッション全体を描いて (ハイライトして) しまう。逆に一度開いた中身を捨てると、閉じる操作が「開いた仕事を捨てる」意味になる。

## Files: 木・本文・リンク

ファイルの画面が答えるのは 3 つ — どこに何があるか (木)、その中身 (本文)、文章の中のパスがどこを指すか (リンク)。

**パスの綴りがそのまま認可の面になる**。契約は `contained` をセッションの根からの相対、`workspace` / `external` を絶対で綴る (契約 `files.ts`) ので、先頭の `/` の有無だけが 3 面の区別になる。木の鍵も、記録した選択も、URL も同じ 1 本の文字列で足りるのはこのため。相対なら `contained` と決まり、**絶対パスの面は `file.stat` に聞く** — `workspace` と `external` は綴りが同じで、どちらが admit するかを答えられるのは instance だけ。

**木は展開時に 1 段ずつ聞く** (`dir.list`)。答えは「聞いた時点の写し」で購読ではないので、再取得は明示のボタン。断られた理由も「答えが出た」側に畳んで覚える — 覚えないと `読み込み中` の行が永遠に残る。

**URL が正本**。`/s/<sid>/files?path=<p>&lines=<a>-<b>` が開いているファイルと指している行を名指しするので、リンクを送れば相手は同じものを見る。ファイルを開くことは navigation で、行は `path` に入れられない (パスは `/` を含む) ため query に置く。**行の名指しは記録より強い** — リンクを送った人は行を指しているので、覚えていた表示モードもスクロール位置も譲る。

**続きは読めない**。`file.read` は instance の読み取り上限 (512KiB) までを答えて `truncated` を立てるだけで、offset を渡す引数を契約が持たない (契約 `files.ts`)。だから先頭だけを出し、なぜここで切れているかをバナーで言う。黙って切ると「そういうファイル」に見える。

**プロジェクト外は履歴であって一覧ではない**。`external` の許可集合はセッションの transcript が名指したファイルで、契約にそれを列挙する op は無い (手元のパスについて admit するかを答える `file.stat` だけ)。なので木に出るのは、このブラウザがそのセッションで実際に開いた絶対パスになる。

**木と本文の境目は動かせる**。掴んで動かすほかに、境目自身が focus を取って ←→ でも動く (WAI-ARIA の `separator` は矢印で動く前提の役なので、掴めるだけでは足りない)。幅は instance ごとに覚える (`ccmsg.layout.split:<instance>`) — 1 つの store に複数の instance が届くという、上の「localStorage のキー規律」と同じ理由。覚えるのは指を離した時だけで、動かしている途中の幅は書かない。読めない値・範囲外は「覚えていない」と同じに扱い、CSS の既定幅に戻す。狭い画面では 2 つが上下に積まれて左右の境目が無くなるので、そこでは境目ごと消える。

**markdown の表示モードはセッション単位の「最後の選択」**。パスごとに持つと、間に `.ts` を 1 つ開いただけで選択が消える (`.ts` に「コードかプレビューか」の答えは無いので、上書きさせない)。

**名前を略して書かれたファイルにも渡りを付ける**。書き手は `docs/issue/2026-09-14-fold-from-head.md` のことを `fold-from-head` と書く。markdown link と違い、これは宣言ではなく推測なので、成立条件は **在ると分かった語にだけ渡りを付ける**こと — 外れが画面に出ないなら、外れは問題にならない。だから語の形の側は緩く、inline code の中身が丸ごとハイフン付きの 1 語であればよい。ハイフンだけが歯止めで、強調のために backtick で囲んだだけの `async` を探しに行かせないためにある。探すのは instance (`file.find`) で、綴りのまま在ればその場で 1 つのリンク、日付 prefix と拡張子を補って初めて名前が合うなら書類の印を出して、押した所に候補を並べる。日付 prefix / 拡張子を緩めるのは webui の側で、契約は変えていない — `file.find` は語が path に含まれるかを答えるので、緩めた綴りでも語そのものは残る。どちらでもなければ何も出さない。

**語をどこから読むかは出している画面が決める**。会話の吹き出しならセッションの作業 folder、文書のプレビューならその文書が置かれている folder — 文書の中の `sibling-notes` が隣を指すのは markdown の読み方そのもので、パスのリンクが従うのと同じ規則。**探した結果自体は場所に依らない**ので、覚えるのは語ごとに 1 回きりで、場所で変わるのは返ってきた並びからどれを選ぶかだけ。**訊くのは画面に出た語だけ** (`in-view.ts`) — 1 つの文書の語の大半は、読み手がそこまで辿り着かない。

## 表示中のものを探す

探す対象は **この画面が今持っているもの** だけ — Timeline の読み込み済みの範囲と、開いているファイルの本文。instance には何も聞かない (DR-0022)。この窓を開くのは 🔍 だけで、打鍵では開かない (下記)。

### 打鍵はブラウザのもの

**既定の割り当ては 1 つも無い。** 人が設定で結ぶまで、この画面はどの打鍵も奪わない。この窓を開くのは 🔍 と、宛先の区画に結ばれた `/` (区画の役、上記) だけ。

クエリは行内の空白が AND、改行が OR。ダブルクオートの句は 1 ワードで、句の中の連続空白は `\s+` に合わせる。`[Aa]` `[.*]` で大小の区別と正規表現に切り替える。**この文法は画面のもので契約にはない** — 契約は daemon と webui が交わす wire の取り決めで、人が窓に打つ文字列の読み方はそこに属さない。

数えるのは「持っているか」であって「今描かれているか」ではない。畳まれた中の一致も `[N/M]` に入り、↑↓ で辿り着く時に囲む fold を開いてから出す (`fold-tree.ts` が囲む fold を答える)。かたまりの単位は **1 item** (と、その中に畳んだ答え) で、名前はその item の id — 遡って手元が前に伸びても、同じ番号が同じ item を指し続ける。ファイルでは行番号が名前になるので、件数と移動はコード表示 (番号付きの行) のもの。プレビュー表示でも光りはするが、段落は名前を持たないので移動先にはならない。

数えた一致は必ず目で追える、を保つ: 道具の呼び出しは 1 行に縮めて出しているので、探す文も**縮めた後の文**にする (`item-view.ts`)。読み込んである全文で数えると「[3/12] と出ているのに 3 番目が見つからない」が起きる。

光らせ方は 2 通りある。地の文は render の時に text を切って `<mark>` を挟む (`markdown-view.tsx` の `text`)。色付け済みのコード行は span の列なので、同じ切り方を span 側に写して切り直す (`splitSpansForHighlight`)。切り直すので、一致が色の境界をまたいでも色は消えない。どちらの形も同じ `<mark>` を出す (`ui/search-marks.tsx`) ので、ファイル本文でも markdown の中のコードでも光り方は変わらない。色が届く前の素のコードは 1 つ目の切り方で光り、届いた後は 2 つ目に変わる。

## 始め方は instance が持っている

セッションを始める献立 — どこで始められるか (`root_dirs`)、どの手順があるか、
その手順がどの値を読むか — は instance の config にあり、画面は
`launcher.config.read` で**聞いた通りに欄を並べるだけ** (`src/ui/Launcher.tsx`)。
手順の名前も変数の名前も config を書いた人の言葉で、こちらで言い換えない。
`launcher` の能力を持たない instance では入口ごと出さない。

手順の中身はそのまま見せ、書き換えられる。端末で打つのと同じことなので隠す理由が
無く、書き換えていなければ送らない (instance が持っている手順がそのまま走る)。
値は文字列として渡り、命令に差し込まれることはない — 変数として渡ることを決めて
いるのは契約の側。

**始めた後は追いかけない**。返ってくるのは走らせた結果 (出力と、終わり方) だけで、
立ち上がったセッションは自分で instance に名乗り、その時に一覧へ出る。プロセスを
見張る画面は持たない。

## 動いていないセッションは instance に探させる

一覧に出るのは instance が今見ているセッションだけで、終わったものや ccmsg を
起動していなかったものはそこに居ない。それを探すのは **instance の仕事** —
transcript の file はその host にあり、ブラウザからは 1 行も読めない
(`session.search`)。画面が持つのは問いと、返ってきた行だけ。

問いの綴りは**画面の中を探す側と同じ** (`parseSearchQuery`): 行内の空白が AND、
改行が OR で、光らせる語もその parser が出したものを使う。instance が探す語と
画面が光らせる語が違っていたら、出ている行のどこが当たったのかが読めない。

空欄は送らない。契約は書かれていない項目を「絞らない」と読むので、空文字を送る
のは「空文字に一致するものを探せ」と言うことになる。遡る幅の既定は 5 日で、綴りを
読めなければ**窓を置かない** — 打ち間違いで黙って狭い窓になるより、広く探して
遅い方が探し物は見つかる。

打ち切られた時は隠さない。`truncated` は「上限に当たった」ではなく「まだあるかも
しれない」で、出ている行が全部だと思って読む方が、探し直すより高く付く。

行を押すとその transcript が開く。生きている接続は要らない — transcript を読む
op は sid で答え、instance は自分の config home の中からその file を見つける。

## 会話は Timeline の上にある

人がセッションに話しかけ、返事を読む画面は別に作らない。**会話の正本はセッションの transcript** で、それを読む画面は既にあるため。往復の 2 方向は transcript の中で違う形をしている。

- **人 → セッション**: `message.send { to: sid, text }`。宛先は sid ひとつで room は無い。届いた 1 通は、セッション側の user turn に `<cross-session-message>` の封筒として現れる
- **セッション → 人**: セッションが走らせる `ccmsg reply <mid> <text>`。`--to` が無い返事は人宛で、instance がそれを通知に変えて届ける

**Enter は改行、送信は ⌘/Ctrl+Enter と送信ボタン** (`src/conversation/composer-keydown.ts`)。書いている途中の改行が打った通りに入ることの方が、1 打鍵で送れることより多くの場面で要る — 手のひらのソフトキーボードでは特にそうで、Enter が送信だと段落を分ける手がそのまま送信になる。IME の変換確定中の Enter は、修飾キーが付いていても送らない (変換を確定した打鍵であって、送る意思ではない)。

どちらの方向も、画面に届く時には `message.session.in` / `message.session.out` という 1 つの型になっている。封筒を読み戻すのも、返事の Bash コマンドから本文を取り出すのも、file を持っている instance の側の仕事 — 同じ文法の写しが 2 つあると、契約が変わっても画面は古い綴りを読み続ける。

## 使用量は gateway のもの、輪はセッションのもの

LLM gateway に関わるものは **hello の `capabilities` で決まる**。`llm_usage` が
無ければクオータの op は呼ばず、`llm_status` / `llm_events` が無ければその topic
を購読しない — 持っていない instance に頼めば断られるだけで、断られたことを
画面に出す意味も無い。gateway を前に置いていない instance では、接続バーの
入口ごと消える。

画面は 2 つの層に分かれる。

- **常駐**: 接続後の道にある入口。上流に**知っている問題がある時だけ**色と印が付く
  (`llm.status` の `overall.severity`)。正常と不明では何も言わない — いつも
  出ている印は、出ていることが意味を失う。不明で画面を赤くするのは、status 頁を
  公開していない provider が 1 つあるだけで全体を異常に見せることになる
- **詳細** (`/usage`): 上流のサービスを先に、クオータを後に置く。数字が動かなく
  なった時に最初に問われるのは上流で、下のクオータの読み方もそれで変わる

**verdict は gateway が決める**。official (provider 自身の言い分) と observed
(この gateway が繋いでみた結果) から severity を導き直すことはしない — 同じ
報告を読む他の全員と違う結論を出すことになる。webui が持つのは言葉と順序だけで、
2 つの signal は列を分けて出す (「稼働中」は主張、「疎通」はやってみたこと)。

**「更新」は人が押した時にしか投げない**。契約が言うとおり、`refresh` を付けた
問い合わせだけが upstream に聞き直し、upstream の rate limit を使いうる (既に
上限に当たっている account では、その credential の error として返る)。定期の
読みが触るのは gateway が持っている写しだけ。credential ごとの limit はその
問い合わせの答えにしか載らないので、押すまで並ばない。

帯は **使った割合と、窓のうち過ぎた割合を重ねて** 描く。割合だけでは使い過ぎが
読めないから — 窓の 2 割しか過ぎていない時の 50% と、9 割過ぎた時の 50% は別の
話で、違いは時計の側にしかない。先行を注意色にするのは 5 ポイント超えてから
(使い方には元々むらがあり、厳密に比べると半分の行がいつも光って意味を失う)。
終わった期間の読みには色を付けない: upstream が「もう数え直した」と言っている
ので、その前の `rejected` は今の話ではない。

prompt cache の輪 (`src/llm/cache-ring.ts`) は **CSS の animation 1 本**で、
負の `animation-delay` で途中から始める。1 秒ごとに JS が進める作りだと、
セッションの数だけ毎秒の仕事が増える。一周は窓まるごとで、固定の 5 分ではない
— gateway は 5 分の cache も 1 時間の cache も張るので、常に 300 秒で切れる輪は
まだ 55 分残っている窓を「切れた」と言ってしまう。輪が言うのは**残りの割合**で、
正確な残り時間は文字の側の仕事。会話が作った窓と、合図が建て直している連なりは
色を分ける (減っているものが別)。連なりを描くのは**窓がまだ生きている間だけ** —
`cache_until_at` はこれから送る合図の予測なので、gateway が送るのをやめた時に
予測の届いていた何時間ぶんも回し続けてはいけない。

## 状態は instance が畳んだもの

セッションが**今何をしているか** (走っている workflow、背後の仕事、TODO) は、
transcript に道具の呼びと答えとして全部書いてある。それを畳むのは instance で、
画面は `session.status:<sid>` で届いた答えを描くだけ (`src/ui/Status.tsx`)。同じ
transcript を読む画面が 2 つあっても、畳み方が 1 つなら答えは 1 つになる。

購読するのは**その tab を開いている間だけ**。URL がその画面を指していることが
「読んでいる」の唯一の根拠で、誰も見ていないセッションの状態まで運ばせない。

並びは**走っているものが先**。読む理由が違う — 走っているものは「今どうなって
いるか」、終わったものは「何があったか」で、後者は薄く沈める。止まっている理由
(`api_error`) はその全部より先に出す: 何も走っていない画面で「暇だから」と
「ここで止まっているから」は別のことで、読む人が次にすることが変わる。

## 端末は端末の一覧で、セッションとはマッピング

**端末はセッションの持ち物ではない** (契約 DR-0026)。人が `zsh -i` で開いた窓はどのセッションのものでもないし、セッションが終わった端末は消えるのではなく一覧に戻る。だから端末はこの build でも独立した一覧 (`/terminals`) と独立した画面 (`/terminal/<id>`) を持ち、URL も根の直下に立つ — セッションの下に置けば、どのセッションにも属さない端末を書く場所が無くなる。

**どのセッションがどの端末に居るかは導出**で、行そのものは何も言わない。突き合わせるのは pid で、それをするのは契約 (`terminalsOf` / `unattachedTerminals` / `starting`) — instance とこの build が同じ 2 つの一覧を 2 通りに読むことが無い。読む `agents` の行は**間引く前のもの**にする (`runRows`): 一覧が自分で出す行を選んだ後の列を渡すと、そこで落ちた run の端末が「誰のものでもない端末」として出てしまう。

**`starting` は「起動したはずなのに来ない」の入口**。ハーネスが走っている端末なのに、その pid の run をまだ誰も名乗っていないという状態で、sid がまだ無いので名乗れるのは端末の id だけ。様子は端末の中にしかないので、セッションの一覧にも端末の一覧にも先頭に出し、案内するのは端末だけにする。

**一覧が優先し、無い時だけ run の言い値に落ちる**。端末管理を持たない instance には端末の一覧そのものが無く、run が状態ファイルから知っている `terminal_id` だけがある (契約 DR-0026 §2)。なので画面が引くのはまず pid の一致、答えが無い時だけ `peers.runs` の値 (`terminalIdOfSession`)。

## 端末は借りて表示する

セッションが動いている端末そのものを開ける。ただし **端末を描くのはこの画面ではない** — instance が `hello` で名乗る gateway (`terminal_gateway`) の画面を iframe に借りるだけで、端末の描画も入力もこちら側には無い。持てば、同じものの二つ目の実装を抱えることになる。

**URL を合成するのは契約** (`terminalUrl`)。端末の handle はどの系の端末かを名乗るもので (`hyoui:<id>` がこの gateway の出す形)、gateway と並べて `<gateway>/sessions/<id>` にする規則は契約に 1 つだけ置く — client ごとに書けば、client の数だけ答えができる。別の scheme の handle からはリンクを作らない (その系を知っている client が開く)。この build が足すのは、自分の読み手に対して負っている 1 つだけ: 値は `href` に入るので、http / https でない gateway からは何も作らない。どちらかの値が無い場合も作らない — 行き先の無いリンクは、リンクが無いより悪い。

**届かないなら出さない**。gateway を名乗らない instance のセッション、端末を名乗らないセッションでは、タブそのものを出さない (`visibleTabs`)。ただし URL の文法は端末のタブを常に読む — 届く場所で作られたリンクは届かない場所でも壊れた URL ではなく、404 ではなくその旨を言う画面に着く。

**セッションの配下に出るのは、そのセッションが今動いている端末**。run が消えれば導出の答えが空になり、端末は一覧の側に戻る — 画面の側で覚えているものは何も無いので、消す処理も要らない。2 つ以上ある時だけどれを見ているかを選ばせる (1 つしかない選択肢は選択ではない)。

**埋め込みと素の URL を区別する**。タブの iframe には `?embed=1&resize=1` を付ける (gateway 側のヘッダを外し、枠の大きさに合わせて PTY を追従させる。埋め込みには設定を出す場所も覚える場所も無い)。一覧の行から開くリンクは gateway の画面そのものなので何も付けず、新しいタブに出す — 一覧を見失わずに端末を覗ける。

## 通知は残さない

`notify` topic の frame は event 粒度で、契約は 1 通も保持しない。webui もページのメモリにしか置かず、切断で捨てる。Timeline の末尾に出る通知の吹き出しは **transcript が追いつくまでの仮の姿**で、同じ返事が transcript に現れたらそちらが正 (吹き出しは破線で、確定した行と同じ重さにしない)。どのセッションを見ていても気づけるように、topbar にも直近の 1 件をトーストで出す。

## 送れない相手には送らせない

composer が有効なのは、**どれかの run に届くセッション**だけ (契約の `liveness` / `reachable`)。止まったセッション宛の `message.send` は instance が断るので、断られてから理由を読ませるのではなく、送れないことと理由 (終了した / 居なくなった / 届かない / 2 つのプロセスが書いている) を先に書く。

送れた場合の応答は 2 つの成功に分かれる: 今届いたか、inbox に積まれたか。積まれた方も失敗ではないので、文言は「待つ / 別のセッションに送り直す / 諦める」のどれなのかを言う (`src/conversation/send-outcome.ts`)。

大きすぎる 1 通も送らせない。契約の `MAX_FRAME_BYTES` は **送る側が守る上限**で、超えた行は instance が `bad_request` で断り接続はそのまま続く。断りに書けるのは大きさのことだけなので、送ってから読ませずに、これから送る行そのものを byte で測って止める (`src/frame-limit.ts`)。分けるかファイルに書くかは送る人が決めることなので、勧めるに留めて選ばない。

## 人は inbox を眺められる

契約の `inbox` は**人も読める** topic で、**人が読んでも配送の印は付かない** — セッションが読むのは配送そのもの (読めばその 1 通は inbox から出る) で、人が読むのは眺めるだけ。人は全セッションの inbox を 1 つの購読で持つので、行は宛先 (`to`) を名乗る。

だから画面が出すのは「この画面が送った控え」ではなく、**instance が待たせている 1 通そのもの**。誰が言った分も出るし、渡った瞬間も instance が言う。畳みは `element` の共通のもの (`ElementFold`、鍵は `mid`)。

消えた 1 通は `removed` の element として来て、**理由が 3 つに分かれている**。読み手が別々に描くのはそこだけなので、画面もそこだけを分ける:

| 理由 | 画面 |
|---|---|
| `delivered` | 消す。同じ 1 通が相手の transcript の item として現れる (`msg_id` が `mid`) |
| `expired` / `dropped` | 行ごと残して印を変える。待っているのと諦められたのが同じ見た目なら、言った人はどちらだったか分からない |

消えた frame には本文が無いので、本文は待っていた間に聞いた分から取る (`departedMessages`、接続と一緒に消える)。

出す場所は **transcript の並びの中、言われた時刻の所** (`withWaiting`)。末尾に寄せると、渡った瞬間に item として別の場所に現れることになる。破線で「まだ記録ではない」と言い、届かなかった分は色を変える。セッション一覧のバッジは待っている通数 (届かなかった分は数えない — 減らない数になる)。

## 通知は答えた 1 通へ戻れる

`notify` の `reply_to` は、その通知が答えた `mid`。同じ答えは通知と transcript の両方に出るので、読み手は 2 つが 1 つのものだと言える鍵を要る。画面はその鍵で飛び先を引き、居る所 (item か、まだ渡っていない 1 通か) へ寄せる。どちらにも居なければ道は出さない。

## 人の認証 (passkey)

正本は daemon の DR-0001 と契約の DR-0030。ここに書くのは **ページが何をどこに持つか**だけ。

| もの | 置き場 | 理由 |
|---|---|---|
| access token | **ページのメモリだけ** (`src/auth/session.ts`) | WS を開ける秘密。store に置けば、この origin で走る全ての script が読める |
| refresh token | **httpOnly cookie** (ページからは読めない) | 読み書きするのは instance で、ページは「送られること」しか関与しない |
| 今ここに居る人 | **ページのメモリだけ** (`user`、契約の `UserId`) | いくつの instance に届いていても人は 1 人で 1 つの値。しかもそれは WebAuthn の user handle そのもので、別に導いた名前ではない (契約 DR-0030 §1) |
| endpoint | **`localStorage`** (`ccmsg.endpoint`)、接続バーで人が述べる | この画面は自分の origin で publish され、繋ぐ先は別の site でありうる。配られた住所は最初に入っている推測で、instance が UI ごと配っている置き方ではそれが正しい |
| passkey の relying party | **どこにも持たない** (`location` から読む) | credential は origin で作られ、その relying party はその origin のホスト (契約 DR-0030 §2) = このページのドメイン。`credentials.get()` には渡さず、`credentials.create()` にもリンクの値ではなく**このページのホスト**を渡す — ブラウザがどのみち断る値から ceremony を組み立てる理由が無い |

**endpoint はページの出所ではないし、2 つを突き合わせもしない。** passkey が答えるのは「どのページから来てよいか」だけで、「どの instance に入ってよいか」は別の record が答える (契約 DR-0030 §§2–3)。だからここで作った passkey 1 本でその人が持つ instance 全部に届き、繋ぐ先は接続バーで人が述べて次の訪問まで覚える。別の instance を述べることは切断そのもの — セッションも一覧も transcript も、それが来た instance のものだから。`/auth/*` への要求は全て `credentials: "include"` で出す。instance がこのページと同じ site でも別の site でも、refresh cookie を運ぶのはこれ (契約 DR-0028)。instance が照合するヘッダ (`Origin`、`Sec-Fetch-Site`) はブラウザが書くもので、ページからは述べられない。

流れは 3 つに分かれ、入口は全て endpoint の `/auth/*` (`src/auth/client.ts`)。endpoint は末尾 `/` の base URL なので、route はその後ろに継ぐだけで引ける (`<endpoint>auth/<name>`、WS は `<endpoint>ws`)。scheme は書き換えない — WS も upgrade する HTTP 要求なので、`https:` のまま `new WebSocket()` に渡す (DR-0001 §2.7)。

- **登録 (enrolment)**: `#enroll=<token>` を持って来た時だけ (`src/auth/enrolment-link.ts`)。claims は表示のためだけに読む (署名を検証できるのは発行 instance だけ)。**6 桁のコードは URL に無い** ので入力させる — URL とコードが別経路で届くことが、URL が漏れても登録にならない根拠。リンクは 2 つのうちどちらをするかを名乗る (契約 DR-0030 §4)。`create_user` は**人を作る** — claims が運ぶ handle に対して passkey を作り、認証器に見せるアカウント名は、URL の推測が既に入っている欄で**本人が決める**。その値は `name` と `displayName` の両方に渡す (passkey manager が保存して一覧に出すのは前者)。`add_owner` は**instance を渡す** — 既に持っている passkey で assert するだけで、作りも改名もしない。claims が名指すのは **origin と endpoint で、何かを決めるのは前者だけ** — origin は人が送られた先であり ceremony が成立してよい唯一の場所なので、別の所で開かれたリンクはその旨を先に言う (ブラウザが誰にも手の打てない言葉で断る前に)。endpoint は答えを POST する先で、何とも突き合わせない (LB の住所でもよい)。接続バーが受けるのはより広い `Endpoint` — instance は平の HTTP でも IP リテラルでも繋ぎに行ける。狭い `Origin` に縛られるのは ceremony を走らせるページだけ。端末ラベルは UA から埋めて人が書き換える (`src/auth/device-label.ts`) — ただし**指の数も一緒に読む**。iPad は自分を Macintosh と名乗るので、UA だけでは Mac と区別できず、タッチ点を返さない唯一の機械が Mac だから。fragment は読み込み時と `hashchange` の両方で読む — 既に開いているタブでリンクを開くと変わるのは fragment だけだから。**使えない URL の断り文句は 1 つ** (使用済み・期限切れ・発行元不明・古い契約の綴り) — どれだったかを言うことは「その URL は本物だった」を言うことでもある (契約 issue `registration-url-checked-before-the-form`)
- **認証**: 「接続」を 1 回押すと、持っている access token → refresh cookie → passkey の順に、そのまま最後まで進む。**押し直させない** — passkey を訊けるのは人が押した直後だけなので、繋ぐことと認証することを 1 回の押下の中で続ける。ボタンの隣では、認証の画面が出ている間だけ、この origin の passkey を**ブラウザ自身の入力候補**に立てておく (`mediation: "conditional"`、`autocomplete="username webauthn"` の欄にぶら下げる) — 久しぶりに来た人が「どのボタンか」を思い出さずに済む形。画面が消えれば候補も下ろす (立てっぱなしの問い合わせは、立てた部品より長く生き残る)。読み込み直後に走るのは人手の要らない所までで (cookie があれば繋ぎ、無ければ「接続」だけの画面で待つ)、認証の話はまだ出さない。passkey が無い / 断られた**その時点で**登録の案内を出す — 登録は端末から始まるので、passkey を持っている人に先に見せるものではない。credential は名指ししない (resident な passkey が user handle で答え、誰かを引くのは instance の仕事)。求めるのは **この origin で作った passkey** で、それはその人が持つ instance 全部に効く
- **期限の延長**: `hello` の `auth_expires_at` が接続の期限。残り 10% で `/auth/refresh` → 同じ接続の上で `auth.extend`。**繋ぎ直さない** — 数時間ごとに画面が瞬く理由が無い

再接続のたびに token を「取りに行く」形にしてある (`Connection` は値ではなく `TokenSource` を持つ)。切れた接続の向こう側で token が期限切れになっていても、その 1 箇所が refresh に落ちるだけで、他はそれを知らない。handshake を拒否された時も同じ口に「取り直し」として落ちる — 持っている token は family のものでページのものではないので、ページが読む期限は「まだ通用するか」を何も語らない。取れなければ**その場で止まる** — 開かない扉を叩き続けても開くのは認証だけなので、繋ぎ直さずに passkey の画面を出し、次に繋ぎに行くのは人が押した時になる。

接続前のボタンは**繋いでいるつもりかどうか**を言う (`wanted`)。隣の状態語は socket が今していることで、再接続の途中は「切断」と「接続中」を行き来する — 意思と状態を分けて持つのが、押した通りのことが起きる形になる。繋いだ後は意思の方が画面から消え (降りる手はハンバーガーの中の「切断」1 つ)、残るのは socket の状態を言う印 1 つになる。

## アカウントは 3 段で 1 枚の絵

`/account` は人が自分の姿を読み返す所 (`src/ui/Account.tsx`、契約 `auth.account.read`)。出るのは **その人・その人に答える passkey・持っている instance** の 3 段。1 枚にまとめるのは問いが 1 つだから — 「この行は自分のものか、外してよいか」に、passkey だけを見ても、instance だけを見ても答えが出ない。

画面を開いた時と、何かを外した後に聞き直す。訪問をまたいで持たない — これらの record は他の instance も書くので、ページが抱えた絵は「もう過ぎたかどうかを自分では判らない瞬間」の写しになる。**外せない行を決めるのは instance** (`auth_in_use`: 今つないでいる instance と、その接続を開いた passkey) で、この画面が二度目の答えを持つことはしない — 先回りしてボタンを殺すと、instance の答えとずれる経路がそこにできる。外す操作は 2 回押させる。取り返しは付くが、戻すには CLI のある端末か別の origin の browser まで歩くことになるから。passkey を足す線上の形はまだ無いので (契約 issue `passkey-list-for-people`)、発行する CLI のコマンドを案内する。

設定の画面と違い、こちらは **instance に聞く**ので繋がっている間しか立たない。色の隣の section ではなく自分の住所を持つのはそれが理由 (DR-0002)。

## 同じセッションのタブは一緒に refresh する

**access token は family のもので、その人が開いている全てのタブが同じ 1 本を提示する** (DR-0001 §2.4)。タブが各自で refresh すると family を回して他のタブの足元から token を抜いてしまうので、ブラウザ側で協調する (`src/auth/tab-share.ts`)。

- refresh (`/auth/refresh` とそれに続く `auth.extend`) は `navigator.locks.request()` の中で走る。1 セッションにつき同時に 1 タブだけ
- 得た結果は `BroadcastChannel` で他のタブへ配る。**メモリ間**で渡す (access token を store に書かないのは上の表のとおり)
- ロックを取ったタブは、refresh する前に同じ channel で**他のタブに尋ねる**。最初に返ってきた token を使う。聞く側に回るのは、ロックと message が別々の queue で渡るから — 他のタブが配ったものはまだ届いていないかもしれないし、自分が開く前に配られたものは二度と届かない。往復の間に誰も答えなければ、それがこのセッションの唯一のタブという意味なので refresh する
- handshake を拒否された時は、まず他のタブが配った最新の token を試してから refresh に落ちる
- Web Locks API が無い環境では各タブが自分で refresh する。これは協調が改善している側の挙動であって前提ではない — 別々に refresh しても収束するのは instance 側の据え置きによる

名前には **endpoint と人** を含める (`ccmsg.auth.refresh:<endpoint>:<user>`、`ccmsg.auth:<endpoint>:<user>`)。理由は下の localStorage のキー規律と同じで、1 つの origin が複数の endpoint を、1 つの endpoint が複数の人を持ちうるから。まだ認証していないタブは誰なのかを知らないので、分かるまでは endpoint だけで聞く。

## localStorage のキー規律

ブラウザの store はサイトに 1 つで、1 人が複数の instance に届く。名前に何を含めるかは、**その値が誰のものかで決まる**。

- **秘密はここに置かない** (上記「人の認証」)。endpoint は置く — ページが自分で読み取れる事実ではなく、「どの instance に届きたいか」という人の申告だから
- **混線するものは instance (と sid) を名前に含める**。認証のロック・channel・セッションの状態のように、**別の instance の同じ名前が別のものを指す**値がこれ。1 つの store から両方に届くので、名前が分かれていないと片方がもう片方を読む
  - session 単位: `ccmsg.<feature>:<instance>:<sid>` の 2 段 (agent の drilldown はさらに `<sid>/<agentKey>`)。書きかけの本文 (`ccmsg.draft:<instance>:<sid>`)、Files タブが覚えている選択 (`ccmsg.files:<instance>:<sid>`) がこれ
  - instance 単位: `ccmsg.<feature>:<instance>` の 1 段。ペインの幅 (`ccmsg.layout.split:<instance>`)、留めたセッション (`ccmsg.sessions.pinned:<instance>`) がこれ — 留めた印は instance の sid を並べているので、instance を名乗る鍵に置く
- **読み方の好みは全体で 1 つ**。色の見え方 (`ccmsg.theme`) と型ごとの表示属性 (`ccmsg.timeline.display:<main|sub>`) がこれで、instance も sid も名前に入らない。「思考は畳む」「道具はトップ層に並べる」は**この人の読み方**であって、どの instance のどのセッションを見ているかの都合ではない — instance で分けると、同じ人が別の instance を開くたびに読み方を決め直すことになる。分かれるのは主語の面 (main / worker) だけで、これは読む理由そのものが違うから
- **ログアウトは既定で全部消す** (DR-0004 §2.6)。`ccmsg.` の付くこの origin のキーを、好みも含めて 1 つ残らず消す — 降りた端末に跡が残るのが既定であってはならない。**残すのは設定を入れた時だけ**で (「切断時にローカルの設定を残す」、既定 off)、その時に残るのは**名前にユーザ・instance・sid のどれも含まないもの** (読み方の好み、並べ方、設定そのもの、ペインの開閉)。**認証・接続・セッションに属するキーはその設定でも残らない** — 名前がそのどれかを名乗るもの (書きかけ、Files の選択、ペインの幅、留めたセッション) と、繋ぎ先そのものの記憶 (`ccmsg.endpoint`) がこれ。残す物を別に列挙しないのは、キーが増えた時にその列挙だけが古くなるから — 名前を作る所がそのまま「これは好みだ」と名乗る (`keepOnSignOut`)
- 消える範囲に**タブ間の取り決めの名前は入らない**。`ccmsg.auth:<endpoint>:<user>` と `ccmsg.auth.refresh:<endpoint>:<user>` は BroadcastChannel と Web Locks の名前で、store には何も書いていない

## 契約の検証は契約の検証器で

届いた topic frame は `TOPIC_SCHEMAS` と契約の `isValid()` に通す。フィールドを 1 つずつ見る検査をここに書かない — 検査は契約の仕事で、通らない frame は「契約の食い違い」という 1 つの結論にしかならないため、警告バナーに落ちる。

## 観測できないもの

**ページは拒否された handshake の HTTP status を読めない。** token が通らなかった時も届かなかった時も、WebSocket API 上はどちらも詳細のない `error` イベントとして届く。ページはそのため「接続を拒否されたか、届きませんでした」としか言えない。

status 自体は消えているわけではなく、**ブラウザの console と network パネルには出る** (Chrome は `Unexpected response code: 401` と書く)。読めないのは JS であって人ではないので、切り分けはそこと daemon のログで行う。

## 契約に無いもの

access token を運ぶ subprotocol の接頭辞 (`ccmsg.token.`) と `/auth/*` のパスは、契約ではなく daemon の入口ポリシー (daemon §3.1、DR-0001 §2.7) にある。`@ccmsg/protocol` は export しないので `src/connection.ts` と `src/auth/endpoint.ts` に置いてある。

## ビルド

**endpoint のパス prefix はビルド時の `base` で決まる** (vite の `base`、既定 `/`)。ページは `location.origin` + `import.meta.env.BASE_URL` を自分の endpoint とするので、prefix 付きで配る instance には **その base でビルドした成果物**を置く (`bun x vite build --base=/personal/` を `https://h.example/personal/` に置く)。現在の `location.pathname` から prefix を推測しない — path はこのページが読む route であって、どこに配られたかを答えられるのはビルドだけ。

**route を読むのも書くのも同じ base から** (`src/base.ts`)。pathname は base を剥がしてから URL 文法に渡し、リンクは base を付けて書くので、`/personal/` に配った成果物では `/s/<sid>/timeline` が `/personal/s/<sid>/timeline` として現れる。base の外の address は unknown route — この成果物が答える場所ではない。文法そのもの (`src/route.ts`) は base を持たず引数で受け取る。リンクの意味が、成果物の置き場所で変わらないようにするため。

dev server は `/ws` `/auth` `/mesh` `/webhook` を daemon (`CCMSG_DEV_DAEMON`、既定 `http://127.0.0.1:39847`) に proxy する。両方を 1 つの origin から配る置き方の reverse proxy と同じ位置に立たせるため。証明書なしで same-site cookie と `localhost` の relying party が得られるのがこの形。別 origin の instance を相手に開発する時は proxy は要らない — 他と同じように endpoint を接続の画面に打てばよい。

**どこへ繋いでよいかは、一覧ではなく形で述べる。** 成果物は CSP の directive を 1 つだけ持つ (`connect-src 'self' https: wss:`、dev ビルドは daemon が答える loopback origin を足す)。instance の許可リストではない — 繋ぐ先は人が述べるもので、繋ぐ先とは独立に publish される UI に許可リストを焼くと、配る場所ごとに、instance を足すたびにビルドが要る。それは UI を別に publish する目的そのものを壊す。他は何も述べない。`default-src` を持たない policy は、名指したものだけを縛る。

帰結を 1 つ明記しておく: **別 origin の平の HTTP の instance は、述べられるが繋がらない。** 入力欄が受けるのは契約 `Endpoint` がそれを許すからで、policy は運ばない。それで失うものは無い — refresh cookie は `Secure` なので、そういう instance はそもそもセッションを運べない。

vite + esbuild の automatic JSX (`jsxImportSource: preact`)。`@preact/preset-vite` は使っていない: 提供するのは prefresh の HMR で、そのために Babel のツールチェーン全体が依存に入る。JSX の変換自体は esbuild が同じ出力を出す。HMR が要るようになったら preset を入れる判断に戻る。

## テスト

**2 つの走らせ方が 1 つの `test/` を分け合う**。`bun test` が読むのは `*.test.ts` で、純関数層 — 契約の畳み方、URL 文法、一覧の並び、jsonl の写像 — をブラウザ無しで固定する。Playwright が読むのは `*.visual.ts` (`test/visual/`) で、こちらは**描かれたもの**を基準画像と比べる。名前で分けているのは、既定の `*.spec.ts` を `bun test` も自分のものとして拾うため。

### 見た目の比較が立っているもの

見た目の比較は本物の上で走る: 使い捨ての config home に **daemon を 1 つ実際に起動**し、dev server を本番の reverse proxy と同じ位置に立たせ、ブラウザは CDP の virtual authenticator で **passkey を本当に登録する**。作り物なのは指だけで、登録も署名も daemon の検証をそのまま通る。セッションは harness を動かす代わりに、session として greeting する接続を書いてある — 本物の Claude Code は pid と時計と誰かの機械のパスを画面に載せるので、そのどれも基準画像にできない。

**基準は面ごとに持つ**。走らせるのは同じ test を 2 度、色の面 (light / dark) だけ
変えて — 同じ画面でも 2 つは別の絵で、片方しか見ていないと、もう片方だけが壊れて
いることに気づけない。置き場は `<platform>/<面>/<画面>.png` で、manifest の鍵も
その 2 段 (`darwin/dark` 等)。platform を分ける理由は下の通りで、色の面は**どちらも
その platform が描く**ので、片方が無ければその場で失敗になる。

**同じ絵が 2 度描けることが、この比較の前提**。だから使い捨てのはずの path と port が固定してある (`test/visual/instance.ts`): 画面に出る endpoint も instance id もそこから derive されるので、乱数の付いた temp ディレクトリでは毎回違う文字列が写る。instance の id は daemon が作る前に置いてあり、transcript は時刻まで書き下した fixture で、残る 2 箇所 — アカウントの画面の、期限の時刻と daemon の版 — だけは mask で覆う。

**画面は既定の好みで描く。** 一覧の幅のように localStorage に残る好みを動かす test は、確かめ終わったら**消して既定に戻す** — 同じ browser context を後の test が使うので、残すと「その後に撮った絵ぜんぶ」がその好みで焼き込まれ、基準画像が走った順番に依存する (その file だけを単体で走らせると一致しなくなる)。

### 基準画像は別リポにある

画像は `kawaz/ccmsg-webui-snapshots` にあり、この repo が持つのは digest だけ (`test/visual/manifest.json`)。基準画像の価値はその履歴 — 同じ画面の、version ごとの並び — で、それは source を clone する全員が払うには重い。manifest が答えるのは「今比べている基準画像は、この version が受け入れたものか」で、画面が変わったこと自体は比較の側が diff 画像付きで落ちる。

**基準画像は描いた platform のものと比べる** (`{platform}/<画面名>.png`)。mac と CI runner ではフォントも smoothing も違い、文字のある所は全部変わるので、閾値では吸収できない。container の中で 1 組だけ描く道もあるが、それは `just visual` に docker を要求する。

- `just visual` — 今の描画を基準画像と比べ、manifest と照合する
- `just visual-accept` — 今の描画を基準にし、snapshots リポに commit する (push は人がやる)。manifest は作業コピーに残るので、画面を変えた commit に一緒に入れる

`just ci` には**入れていない**。要るものが lint/typecheck/test と違う (daemon の source、browser の binary、基準画像リポ) ためで、CI では独立した job になっている。
