# DR-0003: 操作はアクションとして名指し、部品も打鍵も同じものを起こす

Status: Accepted
Date: 2026-09-17

ここに書くのは**なぜそう決めたか / 何を捨てたか**。実装は別で、今の姿を述べる [DESIGN.md](../DESIGN.md) / [DESIGN-ja.md](../DESIGN-ja.md) にはまだ何も無い。設定の器は [DR-0002](DR-0002-settings-are-sections-tried-before-they-are-kept.md)、色は [DR-0001](DR-0001-colour-is-computed-from-a-few-inputs.md)。

## 1. 背景

この画面の操作は、今のところ**押す所と、それが何をするかが 1 か所に書いてある**。行の「改名」ボタンの中に改名の手順があり、検索窓の Enter の中に「次の一致へ」があり、composer の ⌘Enter の中に「送る」がある (`src/conversation/composer-keydown.ts`)。押す所が 1 つしか無いうちは、これで何も困らない。

困り始めるのは、**同じことを別の場所から起こしたくなった時**。TL でメッセージを選び、同じ声の前後へ移る ([docs/issue/2026-09-17-timeline-selected-message-and-voice-nav.md](../issue/2026-09-17-timeline-selected-message-and-voice-nav.md)) は、選んだ吹き出しの ▲ ▼ から起こすが、キーからも起こせた方が速い。一覧を上下に辿るのは押す所すら無く、打鍵でしか意味を成さない。ここで部品ごとに打鍵を足すと、**同じ操作が押す所の分だけ書かれ、どれがどこで効くかを誰も一覧できなくなる**。

打鍵そのものについては既に決まっていることがある — この画面は独自のショートカットを持たず、将来足すとしても既定は無効、ブラウザ標準と被る組み合わせには割り当てない (DESIGN の「打鍵はブラウザのもの」)。**その「将来」の形をここで決める**。決めるのは打鍵の中身ではなく、打鍵が指す先が何であるかと、それが人の設定で結び付くための器。

## 2. 決定

### 2.1 アクション = 名前を持ち、今できるかを自分で言う 1 つの操作

アクションが持つのは 4 つ:

| 持ち物 | 何か |
|---|---|
| id | この画面の中で一意な綴り。設定に書かれるのはこれ (`timeline.select-next-in-voice`) |
| 題 | 人に見せる語。設定の一覧にも、押す所のラベル・`title` にも同じものが出る |
| できるか | 今この瞬間に実行できるか。スコープが立っていることとは**別** (§2.3) |
| 実行 | 呼ばれた時にすること |

**id は綴りであって関数ではない。** 設定に覚えるのも、キーの表が指すのも、`command` 属性に書くのも同じ綴りで、結び付けは実行時に一覧を引いて行う。関数を直に配ると、設定 (= 文字列の世界) から届く先が無くなる。

id は **スコープの綴り + 操作の綴り** で組む (`timeline.`、`session-list.`、`app.`)。どのスコープが担当するかが id を読んだだけで分かる方が、設定の一覧を人が読む時に要る情報が揃う。

### 2.2 スコープは木で、立っているかはアプリの状態が言う

アクションは**階層的なスコープ**に属する。**スコープの木は UI のコンポーネント木と同じ形**で、別に立てた論理的な木ではない。

括弧は今の部品 (`src/ui/`)。印の無いものは未実装。

```
app
├ 未接続
│ ├ 接続の帯 (ConnectionBar)         endpoint 入力 + 接続
│ ├ 登録 (Enrolment)
│ ├ 認証 (SignIn)
│ └ 一覧を聞く前 (Disconnected)
└ 接続後 (Shell)
  ├ グローバルの道 (GlobalNav)       他の画面への入口 + 状態の小部品 (StatusMark) + 読み込み直し (Reload)
  ├ グローバルフッター (GlobalFooter) endpoint の極小表示
  ├ 知らせ (Toast / 再認証のダイアログ Reauth)
  └ workspace (Panes: 接続後の作業画面)
    ├ サイドバー (pane-list)          出す / 出さないが切り替わる
    │ └ セッションリスト (SessionList)
    │   ├ ツールバー (Launcher / SessionSearch)  新規・検索のボタン
    │   └ セクション分けされた一覧
    ├ 境目 (Splitter)
    └ メインコンテンツ (pane-main / Main)
      ├ セッションのヘッダ (SessionTabs)  見方の切り替えと、そのセッションに効く操作のメニュー (SessionMenu)
      ├ tl (Timeline) / files (Files) / 状態 (Status) / 端末 (TerminalPanel)
      ├ run の分岐 (Runs) / 端末の一覧 (Terminals) / 使用量 (Usage)
      ├ 設定 (Settings) / アカウント (Account)
      └ FAB                         どこからでも開くプロンプト入力欄

tl
├ tl ヘッダ      エージェントの一覧と、そのツールバー (このセッションを対象にした検索など)
└ tl 本体
  └ tl ツールバー  検索のボタン、上下のボタン
```

**設定 (Settings) は「接続後」の子で、未接続には設定を置かない**。URL が名指す画面なので、居る所は workspace のメインコンテンツ (`Main`)。キーバインドのような使い方の設定は instance につながっていることが前提になるものが多い。instance に何も聞かない設定 (言語、light / dark) も未接続には出さない — 繋ぐ前の画面に「繋ぐ」以外の道を増やさないため (DR-0004 §2.5)。多言語を世に出す時に、置き場ごと考え直す。

**接続の帯 (ConnectionBar) は「未接続」の子で、接続前の主役**。endpoint 入力と接続を担う。**接続後は帯として存在しない** — endpoint の表示はグローバルフッターに極小フォントで出し、接続状態は道の中の小部品 1 つになる。どちらの根が立つかは `phase` が答える (DR-0004 §2.5)。

**一覧はセッションの内側ではなく兄弟**。サイドバーとメインコンテンツは `workspace` の下で並んでいて、一覧が立っているかどうかはセッションを選んでいるかと関係が無い。id の綴り (§2.1) もこの木をなぞる — `app.` / `session-list.` / `timeline.` は、木の節の名前であって分類ではない。

木の形が UI の形と同じであることが、この設計で一番効いている所になる。押す所は必ずどれかの節の中にあるので、**その押す所が属する節がそのままスコープ**になり、対応表が要らない。画面の作りを変えれば木も一緒に動き、両方を揃え直す作業が発生しない。

**上の図は導出されるものであって、どこかに書いてあるものではない。** 木は**コンポーネントが自分の節を名乗る**ことから組む — 区画になる部品が `<Scope name="tl.body">` のように名乗り、入れ子がそのまま親子になる。図と定義を 2 つ持つと、片方だけが古くなる。そして古くなるのはいつも図の側で、しかも**ずれても何も壊れない**ので、気付かないまま人だけが誤った木を読む。名乗りが唯一の定義なら、区画を動かした時点で木が動く。

**立っているかの判定源はアプリ側の明示的な状態**であって、DOM のフォーカスではない。選択中のセッション、選択中のメッセージ、今の宛先がどの区画か — どれも `signal` として既にあるか、これから置くもので、画面のどこがフォーカスを持っているかとは独立に読める。

DOM のフォーカスを主にしないのは、**当てにならない場面がこの画面に実際にあるから**: 余白をクリックすれば `body` へ外れるが人の意識は TL から動いていない、埋め込んだ端末の中に居ればキーはそもそもこちらへ来ない、`autoFocus` の入力が一瞬だけフォーカスを奪う。フォーカスが外れた瞬間に「今できること」が消える体験は、押す所が消えるのと同じで理不尽に見える。

DOM のフォーカスは**判定源の 1 つとしてだけ使う**: 入力欄 (`input` / `textarea` / `contenteditable`) に居る間は、そこで打った文字が打鍵として解釈されてはならないので、区画スコープを composer / 検索窓に倒す。つまりフォーカスが効くのは「**文字を打っている最中かどうか**」の判定で、そこから先はアプリの状態が言う。

**向きは状態 → DOM の一方向**。立っている節はアプリの状態が正で、DOM の focus は**その節の代表要素へ追従させる** (節の中では roving tabindex で、今のカーソルの要素だけが tab で届く)。逆向き — DOM の focus が動いたら節を決め直す — にはしない。逆にすると、入力欄をクリックしただけで区画が切り替わり、その後の上下が別の所に当たる。人はクリックで「そこを触った」だけのつもりなので、区画まで動くのは予想外になる。

追従させる価値はキーだけではない。**読み上げに「今どの区画か」が伝わる**のは DOM の focus がそこに在る時だけで、状態の中にしか無いカーソルは読み上げられない。下の縁が目に伝えるものと同じことを、focus が耳に伝える。

区画の宛先は**クリックでも打鍵でも移る**。クリックした先の区画を宛先にし、打鍵で区画を移すアクション (§2.7 の `workspace.focus-sidebar`) からも移る。宛先が移ったことは画面に出す — どの区画が今キーを受けるかが見えないなら、キーは当たるも八卦になる。

**見せ方は立っている区画に細い縁**。見出しを立てると区画ごとに場所を取り、何も出さないとキーの当たる先が読めない。縁は色の名前も focus ring と同じものを使う — 「今ここがキーを受ける」という意味は 1 つなので、区画の縁と要素の ring で別の色を持つ理由が無い。太さと濃さは実物を見て調整する。

**フォーカスが指すのは木の節 1 つ**で、アクションはそこから親へ登る。区画をまたぐ移動そのものがアクションになる (「サイドバーへ移る」「tl 本体へ移る」) — 移動が部品の中の副作用だと、どこからどこへ移れるかを人が設定で組み替えられない。

立っている区画に効く方向キーは、その区画が何を並べているかで決まる:

| 区画 | 上下 | ← → | PageUp / PageDown |
|---|---|---|---|
| セッションリスト | セクションとセッションを**兼ねて**辿る (畳んだセクションは 1 単位) | ← は 1 つ外へ (セッションの上ならそのセクションの見出しへ、見出しの上なら閉じる)、→ で開く。セッションの上で → は tl 本体へ移る (Space も同じ) | 区画のスクロール |
| tl 本体 | スクロールと選択に効く | — | スクロールと選択に効く |

セクションとセッションを 1 つの軸で辿るのは、**畳んだセクションが 1 単位に見えることが人の目に映っている通りだから**。軸を 2 つに分けると、今どちらの軸に居るかを人が覚えていなければならない。

**選ぶことと開くことは同じ**。一覧のキー移動はカーソルの行を動かすだけで、開くのは決定 (Enter / →、Space も同じ) の時。カーソルが乗っただけで開いてしまうと、辿る途中の行を全部読み込みに行くことになる。カーソルの行に対しては **tl ヘッダがプレビューとして立つ**ので、開かずに何のセッションかは分かる。

改名・終了・先頭に留めるのような行に効く操作は、**開いている行ではなくカーソルの行**が対象。辿って見つけた行をその場で改名できないと、一度開いてから戻る手数が要る。

**`/` はフォーカス中の区画の検索を開く。** tl なら語の検索、セッションリストならクイックフィルタ。同じキーが区画ごとに違うものを開くのは §2.3 のバブルそのもので、人が覚えるのは「探す」1 語になる。**オフラインのセッションを探すこととセッションのフィルタは別のアクション**で、前者は一覧に無いものを取りに行き、後者は今並んでいるものを絞る — 同じ窓に見えても、聞いている先が違う。

**files はプレビューとツリーでバブルの親が違う。** 木の中でも別々の節なので、ツリーで上下を打つのとプレビューの中で上下を打つのは、別の担当に届く。

### 2.3 起動は内側から外へバブルし、できないものは上へ流す

アクションを id で起こすと、**今立っている最も内側のスコープから外へ向かって**担当を探す。担当を持つスコープが見つかったら、そこで処理して止まる。

同じ id を複数のスコープが担当してよい (`select-next` を timeline も session-list も持つ) — どちらが動くかは今どの区画が宛先かで決まり、人が覚えるのは「次へ」という 1 つの語だけで済む。

**担当はするが今できない (できるかが偽) 時は、既定で上へ流す。** IDE の when 句と同じ既定で、「TL に選択中のメッセージが無いから次へが効かない」時に、外側の一覧の「次へ」が代わりに動く方が、何も起きないより望みに近い。

ただし**流れると困るものがある** — 「終了」がセッションで無効な時に外側の何かが動くのは、危ないか、少なくとも意外。これを止めるのは**アクションごとの上書きではなく `destructive` の印**で、印の付いたアクションは無効時に上へ流さずそこで止まる。

印で括るのは、**止めたい理由が 1 つだから**。終了・強制終了・削除は「間違って起きると取り返しがつかない」という同じ性質で止めたいので、アクションごとに書くと同じ判断を毎回書き写すことになり、新しく足す時に書き忘れる。印なら、危ないものに印を付けるという 1 つの判断だけが残る。印は流れ方だけでなく**見せ方にも効く** — 危ないと分かる色 (DR-0001) と、二段の確認 (§2.8) が同じ印から出る。

「危ない」の線引きが増えていくのは承知の上で、線引きが 1 か所に集まることを採る。

**担当が 1 つも見つからなかった場合は何もしない**。打鍵で起きた場合はブラウザに渡す (`preventDefault` しない) — 割り当ててあるが今は誰も担当しない打鍵で、ブラウザの標準の手まで失うのは筋が通らない。

### 2.4 押す所はアクションを起こすだけ

ボタンの `onClick` は**アクションを起こす 1 行**になり、することの中身はアクション側にある。今そこに書いてある手順はアクションへ移す。

これで揃うのは 3 つ: 押す所とキーが同じものを起こすこと (2 つの経路で挙動がずれない)、押せるかどうかがアクションの「できるか」と同じ所から出ること (`disabled` の判定が 2 か所に無い)、題が 1 か所から出ること (設定の一覧とボタンのラベルが別々に古くならない)。

**押す所を持たないアクションがあってよい。** 一覧へ宛先を移す、上下に辿る — これらは打鍵でしか意味を成さない (押す所を作ると、押した時点でそこがフォーカスを持ってしまい、目的の「手を離さず辿る」が消える)。逆に**キーを持たないアクション**が既定では全部そうなる (§2.5)。

### 2.5 キーバインドは設定の 1 section で、既定は空

キーの表は [DR-0002](DR-0002-settings-are-sections-tried-before-they-are-kept.md) の section 1 つとして持つ。値は **打鍵の綴り → アクション id** の対応で、section が答える 7 つ (`parse` / `format` / `apply` / `changed` / `revert` / `adopt` / `wordFor`) をそのまま満たす。組 (名前付きの一式) も section の中にあるので、「IDE 風」「vi 風」のような一式を後から配れる。

**既定の割り当ては無い。** 人が設定するまで、この画面はどの打鍵も奪わない。

ここで空なのは**アクションへの割り当て**。一覧の上下・← →・決定や、区画ごとの `/` のような「その区画が一覧であること / 検索を持つことの一部」である打鍵は、**部品の中で閉じる操作**として表には載らない (§2.6 の基準で言えば、キーの一覧に「一覧を 1 つ下へ」が並んでいたら変)。`separator` が ← → で動くのと同じ所に居るもので、人が結ぶ表とは別の層にある — 表に同じ綴りを結べば、そちらが先に引かれる。DESIGN の「打鍵はブラウザのもの」の続きで、割り当てが空である限り、人は自分のブラウザの標準の手をそのまま持っている。押す所がある操作は押す所で足り、打鍵でしか届かない操作 (§2.4) は、欲しい人が自分で結ぶ。

#### 打鍵の綴りと、その 3 つの姿

同じ打鍵が、**保存する意味・人が書く綴り・画面に見せる表記**の 3 つの姿を持つ。1 つの文字列に兼ねさせると、どれかが必ず無理をする。

**保存する意味は `{ code, modifiers }`。** `code` は `KeyboardEvent.code` (`KeyK`、`BracketLeft`) で、配列や修飾状態に左右されない物理位置。この画面の打鍵は「あの位置を押す」として手が覚えるものなので、配列を変えても同じ位置に残る方が合う。`modifiers` は集合で持つ — 順序と重複がここで正規化されるので、`Shift+CmdOrCtrl+K` と `CmdOrCtrl+Shift+K` が同じ binding になる。左右の別 (`MetaLeft` / `MetaRight`) はブラウザには見えるが、設定語には入れない。ノート PC・外付け・アクセシビリティ入力で持ち運べなくなる。

**人が書く綴りは `CmdOrCtrl` / `Cmd` / `Ctrl` / `Alt` / `Shift`。** `CmdOrCtrl` は Electron の慣習語で、意味は**今の platform の主要な修飾子 1 つに解決する** — mac なら Command、それ以外なら Control。**Command と Control の論理和ではない。** mac で Command と Control は別の物理キーで、Control は端末の制御文字・Emacs 系の手・VoiceOver が使っている。「どちらでも発火する」にすると、それらを巻き込んで奪う。

`Meta` / `Primary` / `Mod` は採らない。`Mod` は何のキーか読めない。`Meta` と `Super` は製品ごとに Command を指したり OS キーを指したりで一致しない。`Primary` は短く意味も正確だが、`CmdOrCtrl` の方が**綴りを読んだだけで何に解決するか分かる** — 設定を読む人が抽象語を 1 つ覚え直さずに済む。長さより読みやすさを採る。

**今の platform は、2 つの出所のどちらかが mac だと言えば mac。** `userAgentData.platform` (User-Agent Client Hints) と `navigator.platform` (互換目的の古い値) は食い違うことがある — 自動化された Chromium は macOS の上でも前者に `Windows` を返す。片方でも mac だと言えば mac に倒すのは、間違え方の重さが釣り合っていないから: mac を mac でないと読むと `CmdOrCtrl` が Control に解決し、⌘ のつもりで結んだ打鍵がどれも効かない上に Control 側を奪う。逆向きの間違いは、mac でしか起きない予約を余分に断るだけで済む。

**画面に見せる表記は 2 段。** ショートカットの表示 (ボタンの `title`、キーの一覧) は今の platform に解決した形で出す — mac は `⌘⇧K` と記号を繋げ (Apple のメニューに `+` は入らない)、それ以外は `Ctrl+Shift+K` と語を `+` で結ぶ。mac の `Alt` は `⌥`。一方**設定の入力欄には `CmdOrCtrl+Shift+K` の綴りをそのまま置き**、隣に「この環境では ⌘」のように解決結果を添える。記号だけでは設定に転記できず、綴りだけでは実際にどのキーかが分からない。そして添えた解決結果が、これが論理和ではなく**置き換え**であることを目に見せる。

#### binding は platform を限定できる

同じアクションに、**その platform でだけ有効な binding** を結べる。

限定が要る理由は「キーが無いから」ではない。**押せるかどうかは物理キーの有無で決まり、そこに platform の限定は要らない** — ⌘ は mac 限定のキーなのではなく、そのキーがある環境でしか押されないだけ。Windows キーは DOM では `metaKey` として ⌘ と同じ修飾子に見えるが、OS が先に取るので実用上は使えない。半角/全角・変換・英数/かなは、JIS 配列さえあればどちらの OS でも同じ `code` が届く。**存在しないキーは押されないので、そのための限定は書かなくてよい。**

限定が要るのは、**同じキーが両方にあって、ブラウザ側の扱いだけが違う場合**。`Ctrl+F` がそれで、Windows ではブラウザのページ内検索だが mac では誰も使っていない。ここで限定が無いと、mac に合わせた割り当てが Windows で検索を奪う。だから綴りは「他の platform では衝突するので、この platform でだけ」と読む — 「mac 限定のキー」という言い方はしない。

限定は**検査より先に効く**。`Ctrl+F` を mac だけに限定すれば、mac では `Control+KeyF` に解決されてブラウザの ⌘F とは被らず通り、他の platform では**そもそもその行が無い**ので `Ctrl+F` が検索を奪うこともない。

限定を持たない binding は全 platform で有効。既定 (= 何も書かない) は限定無しで、限定は書いた時だけ付く。

#### 断り方は 2 種 — 警告 (通せる) と予約 (通らない)

ブラウザ標準と被る組み合わせを一律に禁止にはしない。**禁止は、こちらの表が現実より広かった時に逃げ道が無くなる**。分けるのは 2 種:

**警告**は、ブラウザの手を奪うが**奪えてしまう**もの。割り当てようとした時点で何が失われるかを言い、それでも良ければ設定に `force` を付けて通せる。自分のブラウザで ⌘F を使わない人から、こちらの都合でその組み合わせを取り上げる理由が無い。

**予約**は、設定に書けても**効かない**もの。ブラウザがページに keydown を渡さないので、`force` を付けても届かない。断るのではなく、**設定できるが効かないことを表示する** — 割り当てたのに何も起きない時、それが自分の書き間違いなのかブラウザの仕業なのかが、画面に出ていなければ人には分からない。

「禁止」を採らないのは、警告を無視する自由と、予約に対して何かを禁じても意味が無いことの両方から。**禁じる必要があるものは 1 つも無く、要るのは「何が起きるかを先に言う」ことだけ**だった。

#### 変換中の打鍵は受けない

IME で変換している間の打鍵は、**どのアクションにも流さない**。事故はいつも同じ 2 つ — 変換を確定する Enter で送られる、変換を取り消す Escape で後ろの何かが閉じる。どちらも人は文字を確定しただけで、打鍵したつもりが無い。

判定は**打鍵を受ける 1 か所**に置く。`isComposing` が立っている keydown と、それを立てない経路で来る `keyCode === 229` を捨てる。加えて **Safari は変換確定の Enter を `compositionend` の後に `isComposing: false` で配る**ので、仕様どおりに読むと確定の打鍵が本物の Enter に見える — だから `compositionend` の直後 1 回に限り、Enter / Escape も確定の側に数える。

入口 1 か所にするのは、composer だけの話ではないから。入力欄の中で閉じる操作 (送る) が自分で見ても、区画の役と人が結んだ打鍵はその外を通るので、同じ判断を 2 度書くことになる。**門は画面ぜんぶで 1 つ**にして、同じ打鍵を 2 人 (入力欄と window) が訊いても同じ答えが返るようにする — 1 人目で印を消すと、2 人目には確定の打鍵が本物に見える。

`page.keyboard` では IME を再現できないので、ここは**合成したイベントの test** で固定する (`test/ime.test.ts`)。

**連続打鍵 (`g` のあと `g`) は持たない。** 1 打鍵目で待つ間の見せ方と、待っている間に来た打鍵の扱いが要る。要ると分かってから足す。綴りを `{ code, modifiers }` の並びに広げる形なので、後から足しても今の綴りは壊れない。

**例外は作らない。** 唯一キーを持っている送る (⌘Enter) は、アクションではなく入力欄の中で閉じる操作として扱う (付録 A) — 書いているものを出す手は、書いている所が持つ。これで「既定の割り当ては空」に穴が開かない。

`Escape` は割り当ての対象にしない。開いているものを閉じる意味は既にあり (`src/markdown/FileWord.tsx`、`src/ui/SearchBar.tsx`)、それは打鍵の割り当てではなく部品が閉じる責務。

### 2.6 アクションにするかどうかの基準

**その部品の外から意味を持つ操作はアクション。** 具体的には、割り当てたい / 別の場所から起こしたい / 画面の遷移や選択の変更を伴う、のどれか。

**部品の中で閉じる細かい操作はアクションにしない。** 入力欄の中のカーソル移動、ピッカーのドラッグ、境目を掴んで動かすこと、ポップを閉じる `Escape`。

迷ったら **「設定のキー割り当ての一覧にその題が並んでいて変ではないか」** で決める。「カーソルを 1 文字右へ」が並んでいたら変で、「次の一致へ」が並んでいたら変ではない。この基準を採るのは、キーの表が人の見る唯一のアクション一覧になるから — 一覧が変に見えないことが、そのまま粒度の正しさになる。

適用した結果は付録 A にある。

### 2.7 最初のアクション群

実装は別だが、器が足りているかは具体で確かめる。§2.2 の木の節ごとに、最初に載るものを挙げる:

| id | 題 | できるか |
|---|---|---|

| `workspace.focus-main` | メインコンテンツへ移る | — |
| `workspace.toggle-sidebar` | サイドバーを出す / しまう | — |
| `main.open-prompt` | プロンプト入力欄を開く (FAB) | URL がセッションを名指している。**送る入口はここだけ** |

**FAB は木の上ではメインコンテンツの子だが、効く先はそこではない** — 書いたものが届くのは**今選んでいるセッション**で、木のどこから開いたかとは無関係。ここで言う「選んでいる」は §2.2 の通り決定して開いた行のことで、一覧のカーソルが乗っただけの行ではない。辿っている最中に書いたものが、目で追っていただけのセッションへ飛ぶのは事故になる。

**宛先を言う signal は持たない** — 決定して開いた行は URL がそのまま名指しているので、宛先の出所は URL の sid 1 つになる。signal を別に置くと、URL と宛先が食い違える形を自分で作ることになり、どちらが正かを決める規則がもう 1 つ要る。worker を読んでいる時の宛先も URL の sid (= その worker を起動したセッション) で、worker 自身は instance に繋いでいないので話しかける相手にならない。

**スコープ木では、FAB はメインコンテンツの節の直下に属する**。files や tl の中身の中ではなく、それらの手前に浮く — どの見方を開いていても同じ 1 つが起きることが、担当をメインコンテンツの節が持つことと同じ意味になる。セッションを名指していない画面では「できるか」が偽で、押す所も出ない。

**送る入口はこの口だけで、transcript の下に据え置きの入力欄は無い**。据え置くと読んでいる所を常に削る上に、files や状態や端末を開いている間は消えるので、同じ「送る」が画面によって在ったり無かったりすることになる。`Composer` 部品はこの窓の中でだけ使う。

**開いた先は口に付く窓で、後ろは不活にしない**。木の上では §2.8 と同じ扱い (開いている間そこが立っている区画になる) だが、器は非モーダル — 画面の真ん中に据えて後ろを止めると、話しかけようとして読んでいた所が見えなくなる。読みながら書けることが、どこからでも開く口の値打ちそのもの。

**ブラウザが既に持っているものを自前で書かない**。この口まわりで使うのは 5 つ:

| すること | 誰の持ち物か |
|---|---|
| 窓を口に付ける | CSS anchor positioning (`anchor-name` / `position-anchor` / `position-area`) |
| 画面の端での折り返し | `position-try-fallbacks` |
| 閉じる (窓の外を押す / `Escape`) | `popover` のライトディスミス |
| 書く所を下へ広げる | `resize: vertical` (textarea 自身の摘み) |
| 書く所が中身に合わせて伸びる | `field-sizing: content` |

自前で書くのは **CSS に無い 3 つだけ**: 口を掴んで動かすこと、書く所の**上**の縁、置いた所と高さを覚えること。外側の click を自分で聞いて閉じる、位置を毎フレーム計算する、といったことはしない — ブラウザの持ち物を写し取った実装は、写した時点の挙動で固まる。

**閉じる手は 3 つある**: 窓の中の押す所、`Escape`、窓の外を押すこと。後ろの 2 つはライトディスミスそのもの。器が `dialog` なら `Escape` はブラウザの持ち物だが、それ**しか**無いと打鍵の無い端末で閉じられない — ホーム画面に追加した PWA で実際にそうなった。

**口は掴んで動かせて、窓は付いてくる**。置き場所は人によっても画面によっても違うので、どこに置くかは人が決める。**窓を開いたままでも動かせる** — 書く所と読む所が重なった時に動かしたくなるのだから、閉じてからでないと動かせないのでは遅い。口が窓を呼んだ所 (`popovertarget`) であることがライトディスミスの除外になるので、掴んでも窓は閉じない。

**居場所は近い側の辺とそこからの距離で覚える** (DR-0002 の section 1 つ、既定は右下)。素の座標で覚えると、端末を回した時・窓の幅を変えた時・ソフトキーボードが出た時に、口が置いた隅から離れ、狭くなった側では画面の外へ出る。辺で覚えていれば、右下に置いたものはどの大きさでも右下に居る。測る先は **visual viewport** で、`position: fixed` の座標系 (layout viewport) とは別 — キーボードが出ている間に layout で測ると、口はキーボードの下に隠れる。既定の隅だけは CSS が持つ (safe-area を避ける余白はそこにしか書けない)。

触っている間は下書きが画面に効き、指を離した所で覚える — 色や幅と違って「試してみて、やっぱり保存」を挟む余地が無い操作で、決める瞬間が指を離す所にある。

| `session.kill` / `kill-force` | 終了する / 強制終了する | 居る (強い方は 1 度普通に頼んだ後) |
| `session.forget` | 失われたセッションを削除する | その行が失われている |

**tl 本体 / 選択中のメッセージ**

| id | 題 | できるか |
|---|---|---|
| `timeline.select-message` | メッセージを選ぶ | TL に item がある |
| `timeline.select-prev` / `select-next` | 前へ / 次へ (スクロールと選択) | 同上 |
| `timeline.open-search` | この TL の中を探す (`/`) | — |
| `timeline.select-prev-in-voice` | 同じ声の前へ | 選択中の item と同じ `voiceOf` / `memberOf` が前にある |
| `timeline.select-next-in-voice` | 同じ声の次へ | 同上 (後ろ) |
| `timeline.show-jsonl` | 元の record (jsonl) を見る | — (選んだ項目がある) |
| `timeline.copy` | 本文をコピーする | 書き込む先をブラウザが持っている |

選んだ項目に効くものの押す所は、**その項目に出る `⋯` の中**に集まる。TL は 1 画面に何百行も並ぶ所なので、項目ごとの操作を据え置くと画面が操作の並びで埋まり、本文が読めなくなる。出るのは選んだ 1 つだけなので、画面に居る `⋯` はいつも 1 つきり — 窓は popover 1 つで足り、錨の名前も id も定数で持てる。

**検索 (窓が開いている間)**

| id | 題 | できるか |
|---|---|---|
| `search.prev-match` / `next-match` | 前の一致へ / 次の一致へ | 一致が 1 つ以上ある |

`select-prev` / `select-next` と `open-search` を、一覧と TL が**同じ末尾の綴り**で持てるか (= 人が「次へ」「探す」1 語で済むか) が §2.3 の狙いそのもので、ここが最初の検証点になる。区画をまたぐ移動が押す所を持たないこと (§2.4) も、ここで最初に効く。

### 2.8 危ないアクションは確認を開くまでが責務

`destructive` の印が付いたアクション (終了・強制終了・削除) は、**呼ばれたら確認のダイアログを開く**。そこまでがアクションの責務で、実際に終了させるのはダイアログの中の決定。キーから起こしても押す所から起こしても同じ 1 つのアクションを通るので、**確認の出ない経路ができない**。今は行の部品が段階 (`asked`) を持っているが、それだとキーから起こした時に段が飛ぶ。

確認そのものはアクションの中に書かない。**ダイアログは木の節を 1 つ持ち** (§2.2)、開いた時点でそこが立っている区画になる。開いたら**既定のボタンにフォーカスが移る** — 既定は定石の側、つまり取り消す方。以後のキーはダイアログの責務で、`Escape` で閉じれば元の区画へ宛先が戻る (閉じる責務は部品のもの、§2.5)。

こう分けるのは、**確認が「もう 1 つの区画」でしかないから**。アクションの中に段階を持たせると、そのアクションだけが他と違う形になり、段階の間のキーがどこへ届くかを別に決めることになる。区画として持てば、フォーカスの追従も `inert` による後ろの不活化も、他の区画と同じ仕組みが使える。

## 3. 不採用

| 採らなかったもの | なぜ |
|---|---|
| **DOM のフォーカスだけでスコープを決める** | この画面では外れ方が多すぎる — 余白のクリック、埋め込んだ端末、`autoFocus` の入力。人の意識が TL にあるのに TL のアクションが消える。フォーカスは「文字を打っている最中か」の判定にだけ使う (§2.2) |
| **部品ごとに独自のショートカットを持つ** | 同じ操作が押す所の数だけ書かれ、どのキーがどこで効くかを一覧できない。人が設定で変えることもできない (変える先が散らばっている) |
| **アクション化せず、今のまま押す所に手順を書き続ける** | 打鍵でしか意味を成さない操作 (一覧を辿る) の置き場が無い。押す所とキーで挙動がずれる余地が残る。ただし**押す所が 1 つしか無いうちは今のままが正しかった** — 2 つ目の経路が要ると分かった今が足し時 |
| **アクションに既定のキーを割り当てておく** | 人の意図に反した動きが最初から起きる。この画面はブラウザの中に居て、人は既に自分の手を持っている (DESIGN の「打鍵はブラウザのもの」) |
| **ブラウザ標準と被るキーを一律に禁止する** | 禁じる必要があるものが 1 つも無かった。奪えてしまうものは警告して `force` で通せばよく、奪えないもの (予約) は禁じても意味が無い — 効かないことを表示するのが人の役に立つ唯一のこと (§2.5) |
| **黙って許す (警告も表示もしない)** | 奪ったことに気付くのは別の作業中で、原因をこの画面だと思い付けない。予約の方は、書いたのに効かない理由が人に分からない (§2.5) |
| **予約の一覧を実機で叩いて作る** | 押して確かめられるのは人が居る 1 台の 1 ブラウザだけで、網羅にならない。しかも確かめている間その機械のキーボードを奪う。Chromium はソースが読めるので、そちらを正本にして実機は裏取りに使う (§2.5) |
| **変換中の打鍵を composer だけで捨てる** | 区画の役と人が結んだ打鍵は入力欄の外を通るので、同じ判断が 2 か所に要る。入口 1 か所に門を置けば、確定の Enter はどこへも流れない (§2.5) |
| **予約の表をブラウザごとに分ける** | 人が今どのブラウザを使っているかをこちらが当てにいく形になり、外した時に何も言わずに効かなくなる。片方でも届かないなら予約として扱う (§2.5) |
| **platform 限定を持たず `CmdOrCtrl` だけで済ませる** | `CmdOrCtrl` が吸収できるのは同じ機能が Command 対 Control で対応している場合だけ。mac の `Ctrl` は他の platform の `Ctrl` と役割が違うので、空いている組み合わせが一致しない (§2.5) |
| **できないアクションを既定で止める (上へ流さない)** | 内側が無効な時に何も起きない。外側の同名が動く方が望みに近い。止めたいものは危ないものだけなので、既定を「流す」にして `destructive` の印で括る (§2.3) |
| **「無効なら止める」をアクションごとに書く** | 止めたい理由は「取り返しがつかない」1 つしかないのに、同じ判断を毎回書き写すことになる。新しく足す時に書き忘れても何も言われない。印なら判断が 1 か所に集まる (§2.3) |
| **修飾キーを `Mod` / `Primary` / `Meta` と綴る** | `Mod` は何のキーか読めない。`Meta` と `Super` は製品ごとに指す先が違う。`Primary` は正確だが、読んだだけで何に解決するかが分からない。`CmdOrCtrl` は長い代わりに説明が要らない (§2.5) |
| **`CmdOrCtrl` を Command と Control の論理和にする** | mac で Control は端末の制御文字・Emacs 系の手・VoiceOver が使っている。両方で発火させると、それらを巻き込んで奪う。解決するのは 1 つだけ (§2.5) |
| **打鍵の照合を `KeyboardEvent.key` で行う** | 配列と修飾状態で値が変わるので、配列を替えた人の設定が意味を失う。この画面の打鍵は位置として手が覚えるものなので `code` が合う。刻印そのものを意味にしたい操作が出てきたら、その時に別の型として足す (§2.5) |
| **連続打鍵 (chord) を今から持つ** | 1 打鍵目で待つ間の見せ方と、待っている間の打鍵の扱いが要る。綴りを並びに広げる形なので、要ると分かってから足しても今の綴りが壊れない (§2.5) |
| **危ないアクションの確認をアクションの中に段階として持つ** | そのアクションだけが他と違う形になり、段階の間のキーがどこへ届くかを別に決めることになる。区画として持てば、フォーカスの追従も後ろの不活化も他と同じ仕組みで済む (§2.8) |
| **確認を押す所の側に持つ (今の `asked`)** | キーから起こした時に段が飛び、確認の出ない経路ができる (§2.8) |
| **1 つの id を 1 つの実装に固定する (スコープごとの担当を許さない)** | 「次へ」が場所の数だけ別の語になり、人が覚える語が増える。同じ語が今の宛先で解決されることが、木を持つ理由そのもの |
| **アクションの一覧を設定 section が持つ** | キーの表とアクションの定義が互いを知ることになる。表が持つのは**綴り**で、実体の一覧はアクション側にある (§2.1)。未知の id が表に残っていても、その行が効かないだけで済む |
| **コマンドパレット (⌘K 風の窓) を先に作る** | 起こす口が増えるだけで、アクションの型とスコープが決まっていなければ作れない。器ができてから足せるものは、器ができてから足す |

## 4. 帰結

- 押す所とキーが同じものを起こすので、2 つの経路で挙動がずれない
- `disabled` の判定と題が 1 か所から出る。設定の一覧とボタンのラベルが別々に古くならない
- 打鍵でしか意味を成さない操作に置き場ができる。押す所を無理に作らずに済む
- 設定を触らない人にとっては**今と何も変わらない** — 既定の割り当てが空なので、打鍵は全部ブラウザのもののまま
- アクションを足す時に触るのは、その定義と、起こす所の 1 行。キーの表にも設定画面にも手が要らない (id と題が自動で並ぶ)
- スコープの判定源をアプリの状態に置いたので、**test に DOM のフォーカスが要らない** — 「選択中のセッションがあり、宛先が TL で、選択中のメッセージがある時に何が担当するか」は状態を組んで確かめられる
- 木が名乗りから導かれるので、区画を動かした時に**木を書き直す作業が無い**。図と定義がずれる余地も無い
- DOM の focus が状態に追従するので、キーで辿った所が**読み上げにも伝わる**。カーソルを状態の中だけに置いていたら伝わらない
- 逆に、**判定源となる状態を持つことが前提**になる。今の宛先がどの区画かは今どこにも無いので、これを置くのが実装の最初の一手

## 付録 B. 使えそうな platform の道具

対象は最新の Chrome / Safari。**採用は実装時に決める** — ここにあるのは、自前で書く前に見る先の一覧。

| 道具 | 状態 | 何に使えるか |
|---|---|---|
| `popover` | Baseline 広く利用可能 | キーの一覧、アクションの一覧 (将来のコマンドパレット)。閉じる手 (Escape・外側クリック・トップレイヤ) が付いてくるので、`FileWord.tsx` が今自前で持っている `document` の `keydown` / `mousedown` が要らなくなる |
| Invoker Commands (`command` / `commandfor`) | Baseline 新しく利用可能 (2025-12 に出揃う) | 押す所がアクション id を**属性で**名乗る形。`command="--timeline.select-next-in-voice"` のように `--` 接頭辞の独自コマンドが `command` イベントで届く。§2.4 の「押す所はアクションを起こすだけ」が、ハンドラを書かずに済む。組み込みのもの (`toggle-popover` / `show-modal`) はスクリプトが届く前から効く |
| `inert` | Baseline 広く利用可能 | スコープの外を丸ごと不活にする。窓を開いている間、後ろの区画がキーもクリックも受けない状態を 1 属性で作れる |
| `focusgroup` | **Baseline ではない** (仕様が 2025 に絞り込まれ、実装は限定的) | 一覧の上下移動を宣言で書けると嬉しいが、当てにできない。roving tabindex は自前で書く前提にする |
| `:has()` | Baseline 広く利用可能 | 「担当が居ない / できない」を CSS だけで薄く見せる。判定を 2 か所に書かない形は DR-0002 §2.2 と同じ |
| `CloseWatcher` | 実装時に状態を確認する | Escape と Android の戻るを 1 つの口で受ける。閉じる責務を部品が持つ (§2.5) 形と合う |
| CSS Anchor Positioning | 実装時に状態を確認する | 選択中の吹き出しに ▲ ▼ を寄せる。今の吹き出しの作りと合うかは実装時に見る |

Baseline の状態は動くので、実装時に webstatus.dev で読み直す。
