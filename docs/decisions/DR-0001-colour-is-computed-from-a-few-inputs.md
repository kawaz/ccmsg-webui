# DR-0001: 色は数個の入力から算出し、部品は意味名だけを書く

Status: Accepted
Date: 2026-09-16

今の姿は [docs/design/color-system.md](../design/color-system.md) と [DESIGN.md](../DESIGN.md) の「Colour is a vocabulary」にある。ここに書くのは**なぜそう決めたか / 何を捨てたか**。

## 1. 背景

色を部品の CSS に直接書くと、同じ役割の色が画面ごとに少しずつ違う値で増えていく。増えた後で「この画面の地をもう少し落ち着かせたい」と思っても、直す場所が何箇所あるか誰も言えない。light と dark を人が別々に選んでいれば、その数は倍になる。

問題は生の値が多いことではなく、**役割の語彙が無いこと**。語彙が無いので部品ごとに値を発明し、テーマの側もそれを追えない。

## 2. 決定

### 2.1 3 層に分け、部品は層 2 だけを書く

層 0 (人が選ぶ入力) → 層 1 (色相ごとの 12 段) → 層 2 (意味名)。部品の CSS が書いてよい色は層 2 の名前だけで、層 1 を直接参照しない。層 0 は部品から見えない。

**段番号は役割を指す**。`--gray-5` と `--danger-5` は同じ役割なので、「この場面だけ中立を危険に差し替える」が段番号を変えずに書ける。段が 12 なのは 12 が切りのいい数だからではなく、画面が実際に区別している役割が 12 個だから。

層 2 の語彙は閉じている。新しい意味名は表に足してから使い、**表に足せない色が要ると思ったら、それは色ではなく別の手段で表す対象**だと疑う。

### 2.2 算出は CSS の相対色構文で行い、JS で色を計算しない

```css
--brand-fill: oklch(from var(--brand) var(--l-9) calc(c * var(--c-9)) h);
```

入力を `:root` に書き換えれば全段が再計算される。テーマを差し替える処理が「入力変数を書く」だけになり、色の算出規則は CSS の中にあるまま — app.css を読めばテーマの仕組みが分かる。

色空間は oklch に一本化する。段を作る操作は「同じ色相のまま L と C を動かす」ことで、oklch はそれを直接書ける。hsl は同じ L でも色相によって明るさが変わるので、段表そのものが成立しない。

### 2.3 読めることは段表に閉じ込め、検査は unit test が持つ

入力から触れるのは色相と色味だけで、L には触らせない。段表が light / dark それぞれで基準を満たすように作られていれば、どの入力を選んでも文字は読める。**コントラストの保証を人の選択の外に出す**ための分け方で、段表をテーマエディタから触らせないのはこの一点による。

比は CSS の式では書けない (WCAG 2 の比は最終的な sRGB の輝度で決まる) ので、検査は `test/color-contrast.test.ts` が持つ。test は `app.css` の層 0 と層 1 を**読んで**解く — 数を test 側にも書くと、片方を直した時にもう片方が古いまま通る。

### 2.4 face で変わる値は `light-dark()` の 1 行に持ち、face を述べるのは `color-scheme` だけ

色相も C 係数も face で動かさない。テーマが変わると中立の温度まで変わる、という結び付きを作らないため。face ごとに違うのは段の明るさだけ。

**段は明るさだけを持つ色として書く。** `--step-9: light-dark(oklch(0.545 0 0), oklch(0.64 0 0))` の 1 行に light と dark の両方が並び、層 2 はそこから明るさを取って入力の色味を載せる (`oklch(from var(--step-9) l calc(var(--brand-c) * var(--c-9)) var(--brand-h))`)。色味を段に持たせないので、中立も意味色も同じ 1 本の段表を使う。

どちらの face で立つかを述べる場所は **`color-scheme` ただ 1 つ**。何も選んでいなければ `light dark` のまま OS が答え、人が選べば `:root[data-theme="light|dark"]` がそれを `light` / `dark` に固定する。この 2 規則は**色の値を 1 つも持たない**。

第 2 の色表を作らないための形でもある。face ごとの値が別の場所に別の名前で住むと、片方だけ古くなる — `light-dark()` なら 2 つの値が同じ行に並ぶので、片方だけ直すことができない。この 2 規則が値を持たないこと、12 段が light と dark を両方持つことは test が見る。

段の明るさを人に触らせないのは §2.3 のとおりで、`light-dark()` の中身は設定画面に出てこない。

### 2.5 主語の色は色相と色味の 2 入力で、色から取り出すのはブラウザにさせる

層 2 が明るさを段から取る以上、`--brand` の明るさはどこにも効かない。だから入力として持つのは `--brand-h` と `--brand-c` の 2 つだけにする。

設定画面はそれでもカラーピッカーで選ばせる (色を選ぶ道具は色を出すものだから)。選ばれた色から 2 つを取り出すのは、相対色構文でブラウザに `oklch()` へ直させて解決済みの綴りを読む — sRGB と OKLCH の間の計算を JS に持つと、色の算出が CSS の外にも住むことになる (§2.2)。

### 2.6 設定画面が触らせるのは層 0 だけで、instance を何も読まない

設定画面は層 0 の入力と face を変える。段表 (L / C) は出さない (§2.3)。

**基本と詳細の 2 段に分ける。** 基本に出るのは face と色相 3 つ (主語の色・自分・ユーザ) だけで、残り — 中立の色味、意味色 4 つの色相、識別の族 — は既定のまま導かれる。色を決める作業を「数個選ぶ」に閉じるのが目的である以上、選ばなくても成立する入力を最初から並べると、選ぶ所がどこかが分からなくなる。

詳細は畳んであり、開くと**残りの入力**が並ぶ。基本に出ているものを詳細にも出さないのは、同じ値を動かす操作子が 2 つ並ぶと、読み上げる人に同じ名前の操作子が 2 度現れて区別が付かないから。基本と詳細は同じ 1 つの入力の組を**分けて**並べたものであって、写したものではない。

だから「基本で選んだ値に詳細が追従する」という仕組みは要らない — 動く値は最初から 1 つしかない。層として比べるものがあるとすれば、それは覚えてある値との差 (§2.10) であって、基本と詳細の間ではない。

この画面は instance に何も聞かない — 色はこのブラウザの見え方であって、instance が言っていることではない。だから**繋がっていなくても、サインインしていなくても立つ**。繋がらない instance を前にした人が、真っ白な画面のまま dark に変えられないのはおかしい。

保存先は localStorage で、キーは instance を名乗らない (`ccmsg.theme`)。どう読みたいかは人のもので、どの instance を開いているかとは関係が無い (DESIGN.md「localStorage keys name what they belong to」)。

### 2.7 誰が言ったかは色相で言い、色相を配るのは store

identity は**色相 1 つ**で、面も罫も文字も同じ色相から段を変えて取る。1 行の色が揃って「1 人分」に見え、同じ人の弱い声 (思考) は色相を保ったまま段が下がるだけで済む。強弱を色相に混ぜると、同じ人の 2 つの声が別人に見える。

人が選ぶ色相は 2 つだけ — **選択中セッションの main** (`--h-main`) とユーザ (`--h-user`)。`self` と呼ばないのは `this` と紛れるうえ、契約にその語が無いから。それ以外の相手の色相は `src/member.ts` が配る: 意味色 4 つと固定の 2 人の前後 15 度を避け、相手の名前から作った希望が空いていればそこ、埋まっていればいちばん広い空きの真ん中へ置く。**一度置いた色相は動かない**。参加者が増えるたびに既に読んでいる行の色が変わると、色で人を覚えるということ自体が成り立たない。

**帯と帯の間に残る狭い隙間には配らない** (幅 30 度未満)。帯から 15 度離れていることと、その色が意味色の仲間に見えないことは別の条件で、危険 (30) と注意 (76) の間は帯を除くと 16 度しか残らず、そこに落ちた相手は「注意」の琥珀と見分けが付かない。狭い隙間は**はじめから空いていないもの**として扱うので、相手が増えて詰まってきてもそこへ落ちてこない — 琥珀に見えることは混み具合と関係が無いから、混んだ時だけ許す形にはしない。

固定の 2 つの既定も**配る時と同じ規則**で決めてある: 意味色を避けた空きのうち、いちばん広い所の真ん中が main (313)、次に広い所の真ん中がユーザ (194)。見分けが目的の色なので、既定も見分けから決まる。

配るのは webui 全体で 1 つにする。開いているセッションによって同じ相手の色が変わると、2 つのセッションを並べて読んでいる人が同じ相手を 2 人だと思う。

名乗りが段 11 ではなく**段 12**、罫が段 7 ではなく**段 8** なのは、色相を機械が配る以上、**円のどこでも**基準を満たしていなければ保証にならないため。識別のために色味を強く取ると、段 11 は色相によって 4.5 を割り、段 7 は 3.0 を割る (`test/color-contrast.test.ts` が 360 度すべてを見る)。名乗りを弱く見せるのは大きさと字面の仕事にする。

この 4 つの意味名だけは `:root` ではなく `.member` の規則が持つ。custom property の中の `var()` は宣言した要素で解決されるので、`:root` に書くと `--member-h` も `:root` のものが読まれ、**誰の行も同じ色になる**。色相を載せる要素と、その色相から段を組み立てる規則は同じ要素に居る必要がある — 層 2 が `:root` に揃うという形より、色が正しく解けることを採る。

型の違い (畳まれた答え、まだ渡っていない 1 通、通知) は罫の形が言う。色相と混ぜない。

### 2.8 声の強さは段で言い、色には乗せない

会話の行は全部が同じ重さではない。主筋はこのセッションと人のやり取りにあり、思考も、別セッションから届いた 1 通も、渡した先の返事も、それに添うもの。全部を同じ枠と同じ字で並べると、**画面がどこを読む所か言わなくなる**。

強さを言う軸は色ではなく、**罫の形と字の大きさと文字の段**にする。色相は既に誰かを言うのに使い切っていて (§2.7)、そこに強さを混ぜると同じ相手の 2 つの声が別人に見える。色味の強さで代わりに言う道も採らない — `--member-*` の段は色相が円のどこに配られても基準を満たす所で決まっているので (§2.7)、強弱のために段を動かすと、その保証が相手の色相次第で崩れる。

下の段の中は**枠を減らして**区別する。枠の量は「どれだけ自己主張するか」をそのまま言うので、3 つの声を色相 0 個で並べられる。思考だけが枠を減らさず破線になるのは、**同じ人が弱く言ったこと**であって別の相手ではないから — 枠の量は相手との遠さの軸で、同じ相手の中では線の形が強さを言う。

呼びかけと、まだ渡っていない 1 通はこの 2 段の外に立てる。transcript の記録ではなく記録になるまでの仮の姿なので、誰かの声の強さとして並べる対象ではない。

段を決めるのは `voiceOf` で、誰かを決める `memberOf` とは**別の関数**にする。同じ `item.type` を読むが、答えているのは違う問い — 1 つの分類器に兼ねさせると、片方の都合で相手の割り当てが動く。

### 2.9 中立の色味は「面の段に掛かった後で見える量」を既定にする

`--neutral-c` の既定を 0.008 に置いていた。段の C 係数は面で 0.2〜0.5 なので、面に残る C は 0.002〜0.004 にしかならず、**無彩の組と並べても差が出なかった**。中立が画面のほとんどを塗っている以上、これは「中立の色相を選べる」と言えていない。

だから既定と上限は「見えるか」ではなく**面の段に掛かった後で見えるか**から決める。段 1 (地) の C 係数を 0 から外したのも同じ理由で、画面でいちばん広い面がそこにある — ここだけ色味を受け取らないと、頁の地は入力に関係なく灰のままになる。

同じことが組にも要る。組が色相しか動かさないと、選び直しても画面は同じ濃さのまま立っていて、**組を選んだことが画面に出ない**。組が持つのは色相と彩度と中立の色味の 3 つとも、とする。

上限を上げることは §2.3 の保証と衝突しない — 段表の L は触っていないので、比を見るのは今まで通り `test/color-contrast.test.ts`。

### 2.10 触ることは試すことで、覚えるのは押した時だけ

色は見てみないと決められない。だから**触った値はその場の画面に出るが、覚えない** — 覚えるのは「保存」を押した時だけで、画面を離れるか読み込み直せば覚えてある色に戻る。「選ぶ」と「決める」を同じ操作にすると、見比べるために動かした値がそのまま残ってしまい、戻す先を人が覚えていなければならない。

値は 3 つの姿で持つ: 覚えてある値 (`saved`)、今画面に出ている下書き (`theme`)、そして**比べる先** (`base`)。比べる先は、組を選んでいればその組、選んでいなければ覚えてある値。差はこの 2 つを項ごとに比べて出し、項ごとに「戻す」を持つ。

差の判定は 1 か所 (`changed`) にしかない。行に印を出すかどうかは、その行の「戻す」が押せるかを CSS が `:has()` で読んで決める — 同じ条件を部品と CSS の両方に書けば、片方だけ古くなる。

**選んでいないことも 1 つの値として比べる。** 「戻す」がその項を消すことである以上 (§2.6)、消えているかどうかが差そのもの。

戻す単位は**画面に出ている操作の単位**に揃える。主語の色は `--brand-h` と `--brand-c` の 2 入力だが (§2.5)、人が触っているのはカラーピッカー 1 つなので、差の印も「戻す」も 2 入力をまとめて 1 行として扱う。

### 2.11 名前付きの組は、既知テーマの特徴色を層 0 に写したもの

組 (プリセット) が持つのは層 0 の入力の値で、段表は持たない。だから組は「コントラストの決まり方」ではなく「入力の初期値」を配るものになる。

**名前は既知のエディタテーマの名前にする。** 「暖色」「寒色」のような自作の名前は、選ぶ前に何が来るか分からないので散文の説明が要り、その説明を読んでもまだ分からない。Solarized や Nord は既に世の中で通っている名前で、**名前そのものが説明**になっている。だから説明は付けない — 名前より説明の方が長くなるうえ、読んだ人が名前から持っている像の方が正確だから。

**採るのは色相と彩度だけで、明るさは採らない。** 段表は全部の組で共通のままなので、**これはそのテーマの厳密な再現ではない**。名前が指すのは「そのテーマの色の選び方」であって、そのテーマのピクセルではない。忠実に再現するには 12 段の L をテーマごとに持つ必要があり (公式パレットの段 9→11→12 は非単調なものがある)、それは層 0 の組ではなく**層 1 の profile** という別の概念になる。何が要るかは実測してあるが (`docs/research/2026-09-17-known-themes-on-the-step-model.md`)、層 0 の組と混ぜない。

**組は face を持つ。** ここは前の判断を覆す。段が `light-dark()` で両方の姿を持っている以上 (§2.4)、入力の組は face を選ばなくてもよい — それは今も正しい。覆るのは**名前の側**で、Solarized Dark は dark のテーマであり、それを light で立てたものはもう Solarized Dark ではない。face が名前の一部になった以上、組がそれを言わないと名前が嘘になる。face を言わない組 (標準) を選んだ時だけ、今立っている face をそのまま連れて行く (`adopt`)。「OS に従う」が組から消える心配は、その標準が受ける。

**意味色と誰かの色の色味も入力にする。** テーマによって発色の強さが違うので (Catppuccin Latte の C 0.21 と Nord の 0.08)、組がそれを連れて来られないと名前だけ借りた別のテーマになる。これも前の判断 (「色相のように選び直すものではない」) を覆す — 選び直す対象ではないという読みは、入力が既定 1 組しか無い間だけ正しかった。

**組ごとにコントラストを測る。** 段表は組が動かさないが、彩度は動かす。緑の弱い文字のように元から余裕の無い所は、ある組でだけ基準を割りうる — 実際 Catppuccin Latte の意味色は公式の平均 (0.172) が段 11 で 4.5 を 0.0015 割った。段表を動かさないと決めている以上、**頭打ちになるのは写す側**で、0.165 に抑えてある。既定の入力だけを測っても保証にならないので、`test/color-contrast.test.ts` は組ごとに、その組の face で測る。

「コントラストの強い組」は**この層では作れない**。コントラストを決めているのは段表であって層 0 ではなく (§2.3)、層 0 で動かせるのは色相と色味だけ。

## 3. 対象ブラウザと、新しい機能の採り方

対象は **最新の Chrome と Safari の 2 つだけ**。Firefox も古い版も保証しない。だから採否は「Baseline の Widely available まで待つ」ではなく「**この 2 つの最新で使えるか**」で決める。新しい機能を避けて昔からの書き方に回る、はしない。

判断は実測に置く。この体系が乗っている機能と、確かめた結果:

| 機能 | この体系での役割 | 実測 (Chromium 153 / WebKit、`CSS.supports` と解決済みの値) |
|---|---|---|
| `oklch()` | 色空間 (§2.2) | 両方で使える |
| 相対色構文 `oklch(from …)` | 段から明るさを取り、入力の色味を載せる | 両方 |
| `light-dark()` | face ごとの値を 1 行に持つ (§2.4) | 両方 |
| **相対色構文の起点が `light-dark()`** | 段表そのもの。これが解けないとこの構造は成立しない | **両方で解け、`color-scheme` に追従する** |
| `color-scheme` | face を述べる唯一の場所 | 両方 |

**`light-dark()` は色にしか効かない。** 段の明るさを色に載せて運ぶのはそのためで、face で変わる非色 (Shiki の斜体と太さ) だけは face の条件を書き下す — CSS に face を見分ける selector が無いので、そこは避けようがない。

## 4. 不採用

| 採らなかったもの | なぜ |
|---|---|
| **ビルド時に色表を生成する** (Bun + culori 等) | 画面を見ながら入力を差し替える用途と両立しない。生成物を `:root` に流し込む形は app.css が値の列挙になり、「CSS を読めばテーマが分かる」性質を失う |
| **JS で段を計算して流し込む** | 同上。色の正本が CSS から JS へ移り、app.css は結果の置き場になる。JS が書くのは層 0 の入力だけに留める。sRGB ↔ OKLCH の変換もブラウザにさせる (§2.5) |
| **`@property` で段や意味名を登録する** | 登録すると計算済みの色として読めるようになる (今は要素に載せて解かせている) が、`initial-value` が要る = 同じ値を 2 か所に書くことになる。補間も要らない (face の切替は一瞬でよい) |
| **`@container style()` で face を切り替える** | 数でも色でも切り替えられるが、`color-scheme` で足りる。face を述べる場所が 2 つになる |
| **`color-mix()` で段を作る** | 相対色構文の方が「明るさは段、色味は入力」をそのまま書ける。混ぜる比率は役割を持たない数になってしまう |
| **相対色構文の無いブラウザ向けに第 2 の色表を持つ** | 色の正本が 2 つになり、片方だけ古くなる。下限を下げる必要が出たら、その時に「入力から作る」をやめる判断ごと見直す |
| **段表を人に触らせる** | コントラストの保証が人の手に落ちる (§2.3)。触れるのは色相と色味だけ |
| **light と dark の色を人が別々に選ぶ** | 選ぶ回数が倍になり、片方だけ古くなる。face で動くのは L の行だけ (§2.4) |
| **Shiki の構文色をこの体系に接続する** | 構文の色は「面の上の役割」ではなく言語の構造を表すもので、段に対応が付かない。接続するのはコードブロックの地と罫だけ |
| **人が選ぶ色相を増やす** (相手ごとに色を選ばせる) | 相手の数は人が決めるものではないので、選ぶ所が増え続ける。固定の 2 人だけを選ばせ、残りは配る (§2.7) |
| **識別の色を意味色から借りる** | 借りると、緑の系列が「うまくいっている」に読めてしまう。見分けが付けばよい色は独立した族 (`--tag-*`) に置く |
| **組が face まで持つ** (「暖色 light」「暖色 dark」) | 同じ入力の組が face の数だけ並び、「OS に従う」が組から選べなくなる。face で動くのは段の明るさだけなので (§2.4)、1 つの組は既に両方の姿を持っている |
| **触った値をそのまま覚える** (保存を持たない) | 見比べるために動かした値が残り、戻す先を人が覚えていなければならない。色は見てみないと決められないので、見るための操作と決める操作を分ける (§2.10) |
| **組を人が作って名前を付けられるようにする** | 覚える対象が「入力の組」から「組の一覧」に増え、消す・並べ替える・名前が衝突する、が全部要る。同梱の組は初期値を配るだけなので、その階層を持たずに済む |
| **差を出すために、覚えてある値と下書きを別々の鍵で localStorage に持つ** | 覚えていないものを覚えることになる。下書きは画面が開いている間だけのもので、読み込み直せば消えるのが仕様 (§2.10) |

## 5. 帰結

- 部品の CSS に生の色値が無い。新しい部品は語彙表から名前を選ぶだけで、選べる名前が無いことが「ここは色で言う場面ではない」の合図になる
- 入力を変えた時に何が壊れうるかは、段表ではなく入力の側に集まる。既定の入力では test が基準を保証するが、**人が色相を大きく動かした先までは保証しない** (§6)
- face で変わる色を新しく足す時に書く場所は `light-dark()` の 1 行だけで、face を見分ける規則を増やさない。`@media (prefers-color-scheme: dark)` を単独で書いた規則は人の選択を無視するので、書けるのは色でない値に限られる (Shiki の斜体と太さ)
- 誰が言ったかの色だけは**色相のどこに来ても**基準を満たす (機械が配る以上、選んだ人が見ていない)。人が選ぶ入力にその保証は無いままで、そこは §7 に残る
- 設定画面が認証と接続の前に立つので、`App` は「URL が設定を名指していれば、繋がっているかを問わずその画面」という分岐を 1 つ持つ
- 下書きは `:root` に書かれた時点で**画面全体に効く**ので、設定画面を離れる時に覚えてある値へ戻す所が要る (画面の unmount がその 1 か所)
- 組を足す・減らすのは配列に行を足すことで済む。組が層 0 しか持たないので、増やしても検査 (`test/color-contrast.test.ts`) の対象は増えない — 段表は動いていない

## 6. 正本からの読み替え

色の決め方の正本は daemon 側の DR-0033 (kawaz 裁定済み) で、v2 はそれを実装したもの。**綴りと段だけが違う**ので、読む時の対応をここに置く。

| DR-0033 | v2 | なぜ |
|---|---|---|
| `--hue-self` | `--h-main` | 固定スロットは「選択中セッションの main」で、`self` は `this` と紛れるうえ契約に無い語。入力の綴りも `--h-info` 等と揃う |
| member の罫は段 7、文字は段 11 (§6.1 / §6.3) | 罫は段 8、文字は段 12 | 色相を**機械が配る**以上、円のどこに来ても基準を満たしていなければ保証にならない。識別のために色味を強く取ると (`--member-c` 0.16)、段 11 は色相によって 4.5 を割り (最悪 4.17)、段 7 は 3.0 を割る (最悪 2.90)。段 12 は 13.0、段 8 は 3.74 で全周通る (`test/color-contrast.test.ts` が 5 度刻みで見る)。段 12 は §6.3 が「通常の吹き出しは段 3 + 文字 12」と言っている段そのもので、段 8 は v2 が色付きの罫に一貫して使っている段。名乗りを弱く見せるのは大きさと字面の仕事にする |
| 希望の色相は cwd を seed にする (§6.2) | 相手の**名前**を seed にする | v2 の transcript item は相手の cwd を持たない。狙い (立ち上がり直した相手が同じ色から始まる) は名前でも満たせる |
| 除外帯は前後 15 度 (§6.2) | 15 度に加え、**幅 30 度未満の空きには配らない** | 帯から離れていることと、意味色の仲間に見えないことは別の条件 (§2.7) |
| 組み込みテーマは「現行配色を再現したもの 1 つから」(§7) | **踏襲しない** | 既存の配色に合わせること自体は目的ではない (kawaz 裁定)。既定は段表と意味名から見て素直な値にする — 意味色は慣習の色相、識別の 2 つは §2.7 の規則で導いたもの |
| 保存の階層・kv op (§7) | DR-0002 §2.5 に設計として置き、実装しない | 契約に汎用 kv op が入ってから |

## 7. 未決

- **入力を変えた結果コントラストが基準を割った時に、画面がそれを言うべきか**。test が見ているのは既定の入力だけで、人が色相を動かした先は誰も見ていない。設定画面がその場で比を出して警告する形はありうるが、今は持たない
- **入力を大きく動かした先で、`light-dark()` の外にある色が浮かないか**。Shiki の構文色はこの体系に接続しないので (§4)、brand の色相を大きく回すとコードブロックの中だけが元の配色のまま残る
