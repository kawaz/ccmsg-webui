# DR-0002: 設定は section の集合で、触ることと決めることを分ける

Status: Accepted
Date: 2026-09-16

今の姿は [DESIGN.md](../DESIGN.md) / [DESIGN-ja.md](../DESIGN-ja.md) の設定の節にある。ここに書くのは**なぜそう決めたか / 何を捨てたか**。色そのものの決まり方は [DR-0001](DR-0001-colour-is-computed-from-a-few-inputs.md)。

## 1. 背景

色の設定画面が先に立った。次に来るものは色だけではない — レイアウト、既定のハイライト語、フォント、部品の大きさ、timeline に既定で出す項目、畳む対象。どれも「この端末でどう読みたいか」で、instance が言っていることではない。

色の画面をそのまま増やすと、**同じ仕組みが設定の数だけ書かれる**。覚える鍵、覚えてある値と触っている値の区別、名前付きの組、ベースとの差、項ごとの「戻す」 — これらはどれも「色だから」要るのではない。2 つ目を書く時に写して、3 つ目で少しずれる。

## 2. 決定

### 2.1 設定 = section の集合、section = 入力の組

`src/settings-section.ts` が持つのは section を**問わない**仕組みだけ: 覚えてある値と下書きを分けること、組を配ること、差を出して項ごとに戻すこと。何が入力で、それがどう画面に効くかは section の側が言う (`Section<V>`)。

section が答えるのは 7 つ — 覚えていた綴りを読む (`parse`)、覚える綴りにする (`format`)、その値で画面を立たせる (`apply`)、2 つの値の違う項を挙げる (`changed`)、何項かをベースへ戻す (`revert`)、組を選んだ時に下書きから何を連れて行くか (`adopt`)、項の名前を画面の語に直す (`wordFor`)。**値の型は section のもの**で、仕組みは `V` として素通しする。

`apply` を section が持つのは、設定が画面に効く道が 1 つではないから。色は `:root` に入力を書くが、次に来るものは DOM でも signal でも file でもありうる。**仕組みが「どう効くか」を知らない**ことが、色以外を載せられる条件になる。

### 2.2 触ることは試すことで、覚えるのは押した時だけ

値は 3 つの姿で持つ: 覚えてある値 (`saved`)、今画面に出ている下書き (`draft`)、**比べる先** (`base`)。触れば `draft` が動いて画面に出るが、`saved` が動くのは `save()` を通った時だけ。画面を離れるか読み込み直せば、覚えてある値に戻る。

これを section ごとではなく仕組みの側に置くのは、**「見てみないと決められない」が色に限らない**から。幅もフォントも語の並びも、当ててみるまで良し悪しが言えない。見るための操作と決める操作を同じにすると、見比べるために動かした値がそのまま残り、戻す先を人が覚えていなければならない。

差は `base` と `draft` を項ごとに比べて出す。**選んでいないこと自体も 1 つの値**として比べる — 「戻す」がその項を消すことである以上、消えているかどうかが差そのもの。行に印を出すかどうかは、その行の「戻す」が押せるかを CSS が `:has()` で読んで決める (判定を 2 か所に書かない)。

戻す単位は**画面に出ている操作の単位**に揃える。1 つの操作が複数の入力を動かすことがある (色の主語の色は、カラーピッカー 1 つで色相と色味の 2 入力が動く)。だから「戻す」が受けるのは名前の並びで、1 つではない。

### 2.3 組は section ごと

名前付きの組が配るのは**その section の入力だけ**。色の組が幅を動かさないのは、組が section の中にあるからで、そう書いてあるからではない。

組が言っていない入力が section にありうる。連れて行くかどうかはその入力の意味で決まるので、section が `adopt` で答える — 色の face は組が言っていればその組のもの、言っていなければ今立っているものを連れて行く (DR-0001 §2.11)。連れて行った先がそのままベースになるので、**組を選んだ直後の差はいつも 0**。

**組の説明は任意にする。** 自作の名前の組には選ぶ前に読む散文が要るが、名前が既に世の中で通っている組 (既知のテーマ名) では名前そのものが説明になる。どちらが要るかは section が知っていることなので、仕組みの側は「あれば出す」に留める。

### 2.4 覚える所は 1 つの文書

localStorage の鍵は `ccmsg.settings` 1 つで、section ごとの部分をその id で持つ。鍵が section の数だけ増えると、消すのも移すのも「section の一覧を知っている誰か」が要る。

色は文書より先にあったので `ccmsg.theme` で覚えていた。文書にまだ色の部分が無い端末では**そちらを読む**。読むだけで、書くのは文書の側だけ — 次に保存した時点で新しい場所に移る。この後始末が色の section の中にあるのは、それが色の来歴であって仕組みの話ではないから。

### 2.5 覚える所の階層は、契約に汎用の置き場ができてから足す

localStorage は**階層の 1 層目**であって、全部ではない。端末をまたいで持ち歩けるようにする時に足すのは、次の形 (DR-0033 §7 の裁定):

| 置き場 | 内容 | 書き手 |
|---|---|---|
| localStorage | いま適用中のもの。触れば即時 | 画面 |
| デバイス固有 | 端末ごとに 1 つ。端末は**人が付けた名前**で同定する | 「この端末に保存」 |
| ユーザデフォルト | 1 つ。どの端末でも始まりになる | 「ユーザデフォルトに保存」 |
| 組み込み | 同梱の組 (読み取り専用) | リポ |

- **ロード順は常に localStorage → デバイス固有 → ユーザデフォルト → 組み込み**。各層は任意で、無ければ親をそのまま使う (暗黙のコピーはしない)
- 画面が出す差は**一つ親の層との差**。今の「覚えてある値との差」(§2.2) と同じ形で、比べる先が 1 つ外側へ伸びるだけ
- 「戻す」は 3 段階 (localStorage を消す / デバイス固有を消す / ユーザデフォルトを消す)。いずれも消したあとロード順で読み直す
- 端末の同定を localStorage の id ではなく人が付けた名前で行うのは、localStorage を消す「戻す」で id まで消えると、その端末のファイルが誰のものでもなくなるため
- instance が複数ある時はユーザの置き場を丸ごとミラーし、決着はファイル単位の last-write-wins。そのため置き場は `updated_at` を最初から持つ

**実装は今しない。** 足せるのは契約に汎用の kv op (DR-0033 §7.1 の形) が入ってからで、テーマ専用の op は作らない — 設定は色だけではないので (§2.1)、置き場も設定の種類ごとに増やさない。

### 2.6 画面は section の一覧を持つ

`/settings` が持つのは section の並びで、1 つずつに「組」「その section の入力」「差の数と保存」を同じ枠で着せる。枠は section を問わない部品 (`src/ui/setting-parts.tsx`) で、入力だけが section のもの。

画面が値の型を知らずに済むよう、store は**型引数の無い面** (`SectionFace`) を併せて名乗る。これが無いと、一覧に並べるために画面側で型を潰すことになる。

次の section を足す時に触るのは 3 つ: section の定義、その入力を描く部品、画面の並びへの 1 行。**仕組みと部品には触らない**。

**入力がその場の手そのものである section は、この並びに載らない**。話しかける口の居場所と高さ (DR-0003 §2.7) がそれで、入力は口を掴んで動かすことと縁を引くことしか無い — 同じことを数字の欄として設定の画面にも置くと、触る所が 2 通りになる。覚える所が文書の 1 項であることは変わらないので、切断で消える範囲も戻し方もここの section と同じ。

### 2.7 選ぶことと見ることは 1 つの操作で、表示例は section の一部

**選ばせるだけでは何も決められない。** 色相の数字を動かしても、それが画面のどこに出るかが見えなければ良し悪しの言いようが無い。だから section は入力の隣に**表示例**を持ち、触る所と効いている所が横に並ぶ (狭い所では縦に積み、触る所が先に来る)。

表示例は section が答えることの 1 つ (`Preview`) で、仕組みの側は中身を知らない — 効き先が画面に出ない設定 (既定の起動先など) は持たなくてよいので、任意にしてある。

表示例に**変える仕掛けは無い**。色なら同じ `:root` の入力を読んでいるだけなので、入力が書き換われば勝手に解け直す。そこに「プレビュー用に値を流し込む」経路を作ると、本物とプレビューで値の道が 2 本になり、片方だけが古くなる。

出すのは**実物の部品**で、見本のために作った四角ではない。見本用の CSS を別に持つと、そちらだけが古くなって「見て選んだ色」と「出てくる色」がずれる。

## 3. 不採用

| 採らなかったもの | なぜ |
|---|---|
| **2 つ目の section を先回りで作る** | 何が要るかは 2 つ目を実際に書く時に分かる。今作ると、色から見えた形をもう 1 つ写すだけになり、一般性の証明にならない |
| **section ごとに localStorage の鍵を持つ** | 鍵が section の数だけ増える。まとめて消す・移す・読むのに、section の一覧を知っている誰かが要る (§2.4) |
| **表示例のために、値を流し込む別の経路を持つ** | 本物とプレビューで値の道が 2 本になる。表示例は普通に画面に立っているものなので、入力が書き換われば一緒に変わる (§2.7) |
| **表示例を見本用の部品で作る** | 見本の側だけが古くなり、「見て選んだ色」と「出てくる色」がずれる。出すのは実物の部品 (§2.7) |
| **daemon に設定を保存する仕組みを今作る** | 契約に汎用の kv op が要る。まず localStorage 1 層で使ってみて、端末をまたいで持ち歩きたいと分かってから足す — 先に階層を作ると、要らなかった時に契約から外せない。足す時の形は §2.5 に決めてある |
| **テーマ専用の保存 op を契約に足す** | 設定は色だけではないので、op が設定の種類だけ増える。置き場は ns と key を持つ汎用のものにする (§2.5) |
| **組を section を跨いで持つ** (「暖色のテーマ一式」) | 色と幅とフォントを 1 つの名前で束ねると、片方だけ変えたい時に名前が意味を失う。束ねたくなったら、その時に「組の組」を足す |
| **`apply` を仕組みが持つ** (「設定は `:root` に書くもの」と決める) | 色以外が載らなくなる。次に来るものの効き先は DOM とは限らない (§2.1) |
| **差を出すために下書きも localStorage に置く** | 覚えていないものを覚えることになる。下書きは画面が開いている間だけのもので、読み込み直せば消えるのが仕様 (§2.2) |
| **section の一覧を仕組みが持ち、画面はそれを描くだけにする** | 入力を描く部品まで section の定義に持たせることになり、定義と UI が互いを import する。一覧は画面のものにして、起動時に要る「覚えてある値を反映する」だけを仕組みが歩く (`applySaved`) |

## 4. 帰結

- 設定が増えても、覚える鍵は 1 つのまま
- 「試している / 決めた」の区別が section を問わず同じなので、人が section ごとに操作を覚え直さない
- section の入力の型は自由 (数でも語でも並びでも)。仕組みは `V` を素通しするだけで、比べ方も戻し方も section が言う
- 仕組みが `apply` を呼ぶ所が 1 か所に集まるので、起動時に覚えてある値を画面へ反映するのも 1 行 (`applySaved()`)
- **仕組みは test に色を要らない**。`test/settings-section.test.ts` は数を 2 つ持つだけの見本 section で回る — 落ちた時に「仕組みが壊れた」のか「色の言い分が変わった」のかが分かれる

## 5. 未決

- **§2.5 の階層を足す時、差の表示が「一つ親」で足りるか**。層が 4 つになると、今見ているのがどの層との差かを画面が言う必要がある。入力の数が少ないうちは横に親の値を出せば足りるが、section が増えた先は分からない
- **section が増えた時に、画面が 1 枚のままでよいか**。今は縦に並べているが、6 つ 7 つになると探す所になる。タブか、左の並びか、検索か — 2 つ目が入ってから決める
- **設定が instance ごとに違ってよいものを持つか**。今の section はどれも「この端末でどう読みたいか」で instance と関係が無いが、そうでない設定 (既定の起動先など) が出てきたら、文書の分け方ごと考え直す
